## Current Focus

hypothesis: The pan-on-select effect at CanvasViewer.tsx lines 380-395 re-fires on every slider-driven render because its dep array `[selectedId, projection, metaQ.data]` includes `metaQ.data`, whose reference changes on every successful refetch — and Plan 04.1-05's introduction of `placeholderData: keepPreviousData` in useCanvasArtifacts.ts did NOT change this invariant (data was already changing ref on success). When user has ANY condado selected (selectedTerritoryId !== null), every slider re-render fires `panToGeoCenter(stage, lon, lat, projection, stage.scaleX(), {mapW, mapH})` → resets `stage.position()` to center the selected territory in the viewport → applyPanClamp re-clamps. If scaledW < viewportW or scaledH < viewportH at the user's current scale, applyPanClamp FORCES x = (vw - scaledW)/2 or y = (vh - scaledH)/2 — centering the map. At a moderate zoom level slightly above minScale, scaledH typically exceeds vh but scaledW may be less than vw (Iberia map is wider than tall), so the X axis gets forced to centered position → user perceives "jump to top-left" because the canvas re-centers horizontally to its smaller-than-viewport scaled-X position. This is the ONLY code path in CanvasViewer that mutates Stage position without also mutating scale.

## Resolution

root_cause: CanvasViewer.tsx line 380-395 selection-pan useEffect has dep array `[selectedId, projection, metaQ.data]`. `metaQ.data` reference changes on every successful TanStack refetch (the `select` function builds fresh objects + `mergedMeta` useMemo deps `[territoriesData, metaData]` both change refs). When σ slider triggers cacheVersion bump → refetch → on success metaQ.data ref changes → effect re-fires → if `selectedTerritoryId !== null`, calls `panToGeoCenter(stage, lon, lat, projection, stage.scaleX(), cfg)` which mutates Stage position to center the selection. Then applyPanClamp forces x = (vw - scaledW)/2 when scaledW < vw — re-centering the map horizontally. User's manual pan to a specific region is overridden. The eslint-disable-next-line at line 394 shows the original author already flagged the dep array as suspect; Plan 04.1-05's `placeholderData: keepPreviousData` did NOT introduce this issue (the ref change happens on every successful refetch regardless), but Plans 04 and 04.1's slider-bumps-cacheVersion pattern surface it now where Phase 03 never did (Phase 03 had no slider-driven refetches).

fix: Gate the panToGeoCenter call on selectedId-CHANGE using a `prevSelectedIdRef` (same idiom as Plan 04.1-03's `prevBoundsKeyRef`). The effect must:
  1. Track previous selectedId across renders via useRef
  2. Only call panToGeoCenter when current selectedId !== previous AND new selectedId is truthy
  3. Keep the existing guards (stage, projection, metaQ.data must be defined to read condado lon/lat)
This preserves the pan-on-selection-change intent (Pitfall 5, panOnSelect tests) AND prevents re-fires on metaQ.data ref churn during slider drags.
