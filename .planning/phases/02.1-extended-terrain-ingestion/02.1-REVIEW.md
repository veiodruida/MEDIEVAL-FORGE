# Phase 02.1: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 30
**Status:** issues_found

## Summary

Phase 2.1 extends the terrain ingestion pipeline with four new SSE-streaming endpoints
(overpass, hydrosheds, dem, ridges), a shared `overpass_client` module, a DEM tile
download+mosaic step, HydroSHEDS basin clipping via geopandas/GDAL, and a DEM-derived
ridge-detection pipeline.

Security posture is good: UUID validation at every endpoint, ISO 3166-1 regex for country
codes, step-name whitelisting on the `/stop` endpoint, integer-only DEM tile URL
construction (T-04-01), and `importlib.resources` for the vendored shapefile path
(T-03-01) all hold up under review. No hardcoded secrets or injection paths were found.

Four warnings were identified — two involve correctness bugs in async code (blocking I/O
on the event loop; silent loss of a stop-event reference when a step is restarted) and two
are edge-case logic issues. No critical issues were found.

## Warnings

### WR-01: Blocking `write_bytes` inside async coroutine in `dem.py`

**File:** `backend/medieval_forge/services/ingest_terrain/dem.py:135`
**Issue:** `tmp.write_bytes(resp.content)` is synchronous, blocking I/O called directly
inside the `fetch_one` async coroutine. A Copernicus DEM tile is typically 5–20 MB; writing
it blocks the entire asyncio event loop for the duration of the disk write. With
`Semaphore(4)` and four concurrent downloads, all four event-loop ticks can stall
simultaneously. The fix is to wrap the write in `asyncio.to_thread` (already used for the
`_merge_to_geotiff` mosaic step on line 160).

**Fix:**
```python
# Replace line 135:
tmp.write_bytes(resp.content)

# With:
await asyncio.to_thread(tmp.write_bytes, resp.content)
```

### WR-02: `register_stop_event` silently overwrites a running task's event

**File:** `backend/medieval_forge/services/ingest_terrain/runner.py:34-37`
**Related:** `backend/medieval_forge/api/terrain.py:41, 58, 74, 98`
**Issue:** `register_stop_event` unconditionally replaces `_STOP_EVENTS[(project_id, step)]`
with a fresh `asyncio.Event`. If a user clicks "Executar" while the same step is already
in-flight (possible via double-click or quick successive calls before the UI disables the
button), the original task's stop-event reference is dropped from the registry. The
`/stop` endpoint will then signal only the replacement event; the first task continues
running to completion, racing the second task on `_write_geojson_atomic`. The atomic
rename protects file integrity but the duplicate network/disk work is undetectable.

**Fix:** Reject a new run if one is already active, or cancel the previous one explicitly:
```python
def register_stop_event(project_id: str, step: str) -> asyncio.Event:
    existing = _STOP_EVENTS.get((project_id, step))
    if existing is not None:
        existing.set()  # cancel any in-flight task before replacing
    ev = asyncio.Event()
    _STOP_EVENTS[(project_id, step)] = ev
    return ev
```

### WR-03: Partial bbox columns yield silent `None` values in `_resolve_bbox`

**File:** `backend/medieval_forge/services/ingest_terrain/runner.py:56`
**Issue:** `_resolve_bbox` checks only `proj.bbox_lon_min is None` before building the
returned tuple. If a prior failed or cancelled ingest left `bbox_lon_min` set but
`bbox_lat_min`, `bbox_lon_max`, or `bbox_lat_max` as `None` (possible when
`_backfill_bbox` raises between column writes), the function returns a tuple containing
`None` values. Downstream callers (`enumerate_tiles`, Overpass queries) receive those
Nones and raise unhelpful `TypeError`/`AttributeError` rather than a clear bbox-missing
error.

**Fix:**
```python
if (
    proj is None
    or proj.bbox_lon_min is None
    or proj.bbox_lat_min is None
    or proj.bbox_lon_max is None
    or proj.bbox_lat_max is None
):
    await queue.put(
        "data: ERROR: project bbox não definido — execute Fase 1 "
        "(ingestão de municípios) primeiro.\n\n"
    )
    return None
```

### WR-04: Discarded `asyncio.create_task` return values

**File:** `backend/medieval_forge/api/terrain.py:42, 59, 75, 99`
**Issue:** Each endpoint calls `asyncio.create_task(...)` without storing the returned
`Task` object. Python docs warn that a task not referenced by a strong variable can be
garbage-collected before it completes if the event loop's internal set is the only
reference. In CPython the event loop holds tasks alive until they are done, so this is
safe in practice — but it is fragile: an alternate runtime or future CPython change could
GC the task early. Additionally, un-awaited tasks whose exceptions propagate unhandled
will log `Task exception was never retrieved` with no traceback in the SSE stream.

**Fix:** Store the task reference and optionally attach a done-callback for error logging:
```python
task = asyncio.create_task(
    terrain_runner.run_terrain_overpass(project_id, queue, stop_event=stop_event)
)
# Prevent silent GC; errors are also logged by the runner itself.
task.add_done_callback(lambda t: t.exception() if not t.cancelled() else None)
```

## Info

### IN-01: Unbounded retry loop in `overpass_client.post_query`

**File:** `backend/medieval_forge/services/overpass_client.py:57`
**Issue:** `while not stop_event.is_set():` has no maximum attempt cap. If all three
Overpass mirrors are persistently unreachable (DNS failure, regional outage), the loop
cycles indefinitely at `min(30, 5*attempt)` second intervals. A user who navigates away
from the UI without clicking "Stop" would leave the background task spinning forever. The
SSE connection is already gone but the asyncio task is still alive and consuming CPU/memory.

**Fix:** Add a configurable attempt ceiling (e.g., `MAX_ATTEMPTS = 30` ≈ 15 minutes of
retries at full backoff) and raise `RuntimeError` with a clear message when exceeded.

### IN-02: Degenerate centerline fallback in `ridges.py` produces near-zero-length geometry

**File:** `backend/medieval_forge/services/ingest_terrain/ridges.py:108-109`
**Issue:** When a ridge polygon contains fewer than two skeleton pixels, `_skeleton_to_line`
returns `LineString([(cx,cy),(cx+1e-6,cy+1e-6)])` — a ~0.1-millimeter line. Downstream
consumers that compute ridge length, simplify geometry, or buffer the centerline may
produce unexpected results or errors from degenerate geometry. The comment says this is
"for visualization only" but the GeoJSON contract does not document this special case.

**Fix:** Either set the geometry to `None`/skip the feature for degenerate polygons, or
use the polygon's long-axis diameter as the fallback line, and document the behavior:
```python
if len(xs) < 2:
    # Degenerate: polygon with no skeleton pixels — return centroid point as stand-in.
    cx, cy = poly.centroid.x, poly.centroid.y
    # A zero-length line is invalid GeoJSON; use a Point instead if API consumers allow it.
    return LineString([(cx - 1e-4, cy), (cx + 1e-4, cy)])  # ~10m line along latitude
```

### IN-03: Hash collision risk for ridge IDs when elevation stats return zeros

**File:** `backend/medieval_forge/services/ingest_terrain/ridges.py:73, 87-88`
**Issue:** `_stable_ridge_id` hashes `f"{cx:.3f}|{cy:.3f}|{int(round(elev_max))}"`.
`_elev_stats` returns `(0.0, 0.0, 0.0)` when no valid (non-nodata) pixels fall inside
the polygon (line 87-88). If two ridge polygons have centroids that round to the same
three-decimal-place coordinate and both have `elev_max=0`, they produce identical IDs.
With large nodata regions this could happen in coastal or border DEM tiles. The collision
would cause downstream systems keyed on `id` to silently merge two distinct ridges.

**Fix:** Include the polygon's area or a sequential index as a tiebreaker in the hash key:
```python
key = f"{centroid_x:.5f}|{centroid_y:.5f}|{int(round(elev_max))}|{poly.area:.8f}"
```

### IN-04: Shared log always shows first-in-array step with lines, not most-recently active

**File:** `frontend/src/components/pipeline/TerrainDataSection.tsx:66`
**Issue:** The fallback for `sharedLog` when no step is actively running uses
`all.find((s) => s.lines.length > 0)` where `all = [overpass, hydrosheds, dem, ridges]`.
`Array.find` returns the first match in array order. After running DEM and then running
and completing overpass again, the log shows the DEM lines (first array entry with lines)
rather than the most recent overpass lines. This is confusing UX — users expect the log
to show the most recently executed step.

**Fix:** Track the most recently completed step explicitly, or reverse the search order:
```typescript
// Show the last step that has lines (most recently populated), not the first.
const sharedLog = active
  ? active.lines
  : ([...all].reverse().find((s) => s.lines.length > 0)?.lines ?? [])
```
