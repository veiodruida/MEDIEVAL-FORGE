# Phase 2.1: Extended Terrain Ingestion — Context

**Gathered:** 2026-04-29
**Status:** Ready for planning

<domain>
## Phase Boundary

The system fetches all natural-boundary data needed for geometry-first territory construction (Phase 2.2) — rivers, peaks, coastline, parishes (via OSM Overpass), HydroSHEDS basin polygons (vendored), and Copernicus DEM 90m raster + derived ridges — for any project bbox. Each dataset lands in `raw/` as either a valid GeoJSON `FeatureCollection` (Shapely-readable) or a GeoTIFF, and each step is independently triggerable from a new "Terrain Data" UI section with live SSE progress and stop-event cancellation.

Out of scope: territory construction (Phase 2.2), LLM research (Phase 3), bathymetry / navigable sea regions (deferred), canvas rendering of new datasets.

</domain>

<decisions>
## Implementation Decisions

### Overpass (rivers / peaks / coast / parishes — GEO-01..04)
- **D-01:** Four separate Overpass calls, one per dataset, each writing its own `raw/<dataset>.geojson`. Keeps GEO-01..04 independently re-triggerable and parsing per-step is simpler.
- **D-02:** Reuse the 3-mirror infinite-retry + `stop_event` cancellation pattern from `services/ingest_osm.py` (`OVERPASS_ENDPOINTS` rotation). Extract into a shared helper consumed by both Phase 1 municipalities ingestion and the new terrain calls — same UX, same "Parar ingestão" button.
- **D-03:** Coastline is multi-segment by nature: load all OSM coastline ways, run `shapely.ops.line_merge` to connect endpoint-to-endpoint, output as `MultiLineString`. Polygonization (terra/mar) is deferred to consumers (Phase 2.2 / generator land mask).
- **D-04:** Parishes (`admin_level=8`) degrade gracefully when the country lacks them: write a valid empty `FeatureCollection` (`{"type":"FeatureCollection","features":[]}`) and emit an SSE log line `Sem parishes disponíveis para {country}`. Phase 2.2 must treat parishes as optional input.

### HydroSHEDS basins (GEO-05)
- **D-05:** Vendor the full world `hybas_lev06_v1c.shp` (~150MB) inside the Python package via `package_data`. Works fully offline, deterministic, no first-run download stall. License attribution (CC-BY) lives in `backend/medieval_forge/data/hydrosheds/LICENSE.txt` and the README.
- **D-06:** Read shapefile at runtime with `geopandas.read_file(..., bbox=project_bbox)` and write the clipped result via `to_file(..., driver="GeoJSON")`. Stable feature id = native HydroSHEDS `HYBAS_ID` (preserves cross-project consistency).

### DEM (Copernicus 90m — GEO-06)
- **D-07:** Source: AWS S3 public bucket `copernicus-dem-90m` in `eu-central-1`, fetched via plain HTTPS GET with `httpx` (range requests) — no `boto3`, no AWS credentials. Tile naming: `Copernicus_DSM_COG_30_N{lat}_00_E{lon}_00_DEM.tif`.
- **D-08:** Download concurrency = **4 tiles in parallel** (asyncio.gather) — sweet spot for residential ISPs and SSE log readability. Iberia ~24 tiles → ~6 batches.
- **D-09:** Tile cache: `data/dem_cache/` shared across all projects (DEM tiles are global). Filename per `Copernicus_DSM_COG_30_N{lat}_00_E{lon}_00_DEM.tif`. **Never auto-evicted** — manual cleanup only.
- **D-10:** Server-side mosaic via `rasterio.merge.merge(...)` running inside `asyncio.to_thread` to avoid blocking the SSE generator. Final SSE event `mosaic_complete` fires when `raw/dem.tif` has been written.
- **D-11:** Output CRS = native **EPSG:4326** (no reprojection at ingestion time). Nodata = native **-32768** preserved (don't fill ocean — coastline + DEM nodata is what enables future land/sea distinction).
- **D-12:** Pin `rasterio>=1.4,<1.5` (1.5+ requires Python 3.12; project targets 3.11+).
- **D-13:** DEM step is independently triggerable — it depends only on `project.bbox`, never on coastline being already ingested.

### Ridge derivation (GEO-07)
- **D-14:** Library: **numpy + scipy + scikit-image** as primary (slope/curvature laplacian → threshold → `skimage.morphology.skeletonize` → polygonize). **whitebox is opt-in** via `pip install medieval-forge[high-quality]`. If the user picks "high quality" sensitivity without the extra installed, the server returns 412 with the install hint.
- **D-15:** `raw/ridges.geojson` features carry **both** `MultiPolygon` (buffered ridge zone — used by Phase 2.2 for cross-ridge adjacency penalty) and a sibling `LineString` centerline (visualization).
- **D-16:** Validation criterion (test): cross-reference clusters of OSM `natural=peak` features in `raw/topography.geojson` — every cluster of ≥N peaks within R km must be covered by ≥1 ridge polygon. No hardcoded "Pyrenees / Sierra Nevada" — generalizes to other countries.
- **D-17:** Tunable per-run via a `low/med/high` Radix Slider inside the Ridge `StepCard`. Mapped server-side to threshold tuples. Not persisted across projects.
- **D-18:** Time budget = **<60s target, fail-soft** (warn in SSE log if exceeded; do not abort).
- **D-19:** Feature schema (rich): `{id, name?, elev_min, elev_max, elev_mean, peak_count, basin_ids[]}`. `name` populated when OSM peak cross-ref identifies a known range.

### Bbox source
- **D-20:** `project.bbox` = `shapely.unary_union(municipalities_features).bounds` computed **once** at the end of Phase 1 ingestion and persisted on the `Project` row in SQLite. All Phase 2.1 steps read this column. No user-drawn UI for v1.
- **D-21:** Large-country guard: if bbox span > 30°×30°, the server transparently splits requests (Overpass: per sub-bbox; DEM: tile list already per-tile). No user-facing error or warning — pure plumbing.

### Phase 2.1 → 2.2 contract (mandatory in CONTEXT.md)
- **D-22:** Document a **dataclass-style schema per `raw/*.geojson`** in this file (see `<contract>` section below). The Phase 2.2 planner will code against this schema without re-reading raw files.
- **D-23:** **Stable, deterministic IDs** for every feature so re-runs of Phase 2.1 don't invalidate Phase 2.2 / Phase 3 outputs:
  - Rivers: OSM `way` id (already stable).
  - HydroSHEDS basins: native `HYBAS_ID`.
  - Ridges: `sha1(round(centroid.x,3), round(centroid.y,3), round(elev_max))[:12]`.
  - Coastline: not feature-keyed (single MultiLineString).
  - Parishes: OSM `relation` id.

### Pipeline UI + re-run (GEO-08)
- **D-24:** New collapsible "Terrain Data" section sits **above** the existing Phase 1 Stepper in `ProjectDetail`. Not inside the stepper — keeps Phase 1's linear flow visually separate from prerequisite-for-2.2 datasets. Collapsed by default; header badge shows `N/4 datasets prontos`.
- **D-25:** Four `StepCard`s inside, one per dataset: **Overpass terrain** (rivers + peaks + coast + parishes — single combined card emitting 4 files), **HydroSHEDS basins**, **DEM (Copernicus)**, **Ridges (derive)**. Cards reuse the existing `frontend/src/features/pipeline/StepCard.tsx`.
- **D-26:** Re-trigger semantics: clicking the run button on any step **always re-runs and overwrites** `raw/<file>` (no skip-if-exists prompt). DEM tile cache (`data/dem_cache/`) still reduces re-download cost.
- **D-27:** Status signaling: each `StepCard` shows a Radix Badge (`pendente` cinza / `rodando` azul / `pronto` verde / `erro` vermelho) plus a shared SSE log panel below the section that streams the currently-active step's messages — same UX vocabulary as Phase 1 ingestion.

### Testing strategy (Wave 0)
- **D-28:** **Wave 0 RED tests first**, GREEN in subsequent waves — same TDD pattern as Phase 1. Each plan opens with failing tests; implementation waves make them pass.
- **D-29:** Overpass tests use captured-response fixtures: `tests/fixtures/luxon-bbox.json` (~0.5°×0.5° Luçon, MA — small enough for fast tests) plus `tests/fixtures/responses_recorded/overpass_{rivers,peaks,coast,parishes}.json` replayed via `respx` / `httpx_mock`. Zero real network in unit suite.
- **D-30:** Ridge derivation tests use a **synthetic DEM**: `tests/fixtures/synthetic_dem.tif` is a numpy array with two gaussian peaks at known coordinates. Test asserts ≥2 ridge polygons cover the gaussian centers.

### Claude's Discretion
- Internal helper names, module layout (`services/ingest_terrain/` vs flat files), exact slope/curvature threshold tuples per low/med/high preset, SSE message wording, AsyncIO semaphore vs gather chunking for the 4-concurrent DEM downloads, and HydroSHEDS attribution placement details. The planner picks these.

</decisions>

<contract>
## Phase 2.1 → 2.2 Output Contract

Phase 2.2 (`territories_builder.py`) and Phase 3 (LLM research) consume these files. Schemas below are normative — do not deviate without updating this contract.

### `raw/rivers.geojson` (GEO-01)
```
FeatureCollection
  feature.geometry: LineString | MultiLineString  (EPSG:4326)
  feature.properties:
    id: int                # OSM way id (stable)
    waterway: "river" | "stream"
    name: str | null
```
Invariant: `properties.waterway ∈ {"river","stream"}`.

### `raw/topography.geojson` (GEO-02)
```
FeatureCollection
  feature.geometry: Point  (peaks) | LineString (ridges) | LineString (cliffs)
  feature.properties:
    id: int                # OSM node/way id
    natural: "peak" | "ridge" | "cliff"
    name: str | null
    ele: float | null      # meters, may be missing
```

### `raw/coastline.geojson` (GEO-03)
```
FeatureCollection
  feature.geometry: MultiLineString  (single feature post-merge)
  feature.properties: {} (intentionally empty — coastline is unkeyed)
```

### `raw/parishes.geojson` (GEO-04)
```
FeatureCollection (may be empty for countries without admin_level=8)
  feature.geometry: Polygon | MultiPolygon
  feature.properties:
    id: int                # OSM relation id
    name: str
    admin_level: 8
```

### `raw/basins.geojson` (GEO-05)
```
FeatureCollection
  feature.geometry: Polygon | MultiPolygon  (HydroSHEDS lv6 clipped to bbox)
  feature.properties:
    id: int                # HYBAS_ID (HydroSHEDS native, stable)
    next_down: int         # downstream HYBAS_ID
    sub_area: float        # km²
```

### `raw/dem.tif` (GEO-06)
```
GeoTIFF, EPSG:4326, nodata=-32768, dtype=int16, ~90m resolution
Mosaiced from Copernicus DSM 30 (90m) tiles for project bbox.
```

### `raw/ridges.geojson` (GEO-07)
```
FeatureCollection
  feature.geometry: GeometryCollection of [MultiPolygon, LineString]
                    # MultiPolygon = buffered ridge zone (for adjacency penalty)
                    # LineString   = centerline (for visualization)
  feature.properties:
    id: str                # sha1(round(centroid),round(elev_max))[:12] — deterministic
    name: str | null       # populated when OSM peak cluster matches a named range
    elev_min: float
    elev_max: float
    elev_mean: float
    peak_count: int        # OSM peaks within polygon
    basin_ids: list[int]   # HYBAS_IDs intersected (cross-basin ridge tagging)
```

</contract>

- `services/ingest_osm.py` — `OVERPASS_ENDPOINTS` list + the 3-mirror infinite retry loop with `stop_event`. **Extract** into a shared helper (e.g. `services/overpass_client.py`) so the 4 new terrain queries don't copy-paste the rotation.
- `services/ingest_runner.py` — SSE streaming pattern for ingestion (the `data: ...` event protocol the frontend already understands). New terrain endpoints emit the same shape.
- `frontend/src/features/pipeline/StepCard.tsx` + `Stepper.tsx` — already used for Phase 1; new "Terrain Data" section composes 4 `StepCard`s inside a Radix `Collapsible.Root`.
- `useIngestStream` hook (frontend) — generic SSE consumer with `AbortController.signal`; one new hook (`useTerrainStepStream`) can wrap it 4×.
- `services/paths.py` — T-PATH guard for `raw/` writes; reuse for new files.

### Established Patterns
- **Atomic writes**: existing ingestion writes to `raw/<file>.geojson.tmp` then `os.replace` — keep this for all 5 new files (rivers, topography, coast, parishes, basins, ridges).
- **SSE event vocabulary**: `data: <message>\n\n` plain text lines, with the front-end log panel just appending. New steps follow the same shape — no JSON envelope unless absolutely needed.
- **Stop button**: a single `stop_event = asyncio.Event()` per ingestion run; the cancel endpoint sets it. Reuse for terrain steps.

### Integration Points
- `backend/medieval_forge/api/` — add a new `terrain.py` (or extend `ingest.py`) registering POST endpoints for each step + their SSE counterparts.
- `models.py` — add `Project.bbox` column if not already present (D-20). Migration via Alembic.
- `frontend/src/features/pipeline/` — new `TerrainDataSection.tsx` containing 4 `StepCard`s + collapsible header. Mounted in `ProjectDetail` above the existing `Stepper`.
- `pyproject.toml` — add deps (`geopandas`, `rasterio>=1.4,<1.5`, `scikit-image`, `httpx[http2]`), `package_data` for HydroSHEDS shapefile, optional `[high-quality]` extra for `whitebox`.

<specifics>
## Specific Ideas

- **Stop_event reuse is a hard requirement**: the user specifically validated the pattern in `quick-260428-nwl-02` (Parar ingestão button + AbortController). Every new terrain step must honor it.
- **Wave 0 RED tests are non-negotiable** (D-28) — same discipline as Phase 1. The planner should structure each plan with Wave 0 = failing tests.
- **HydroSHEDS attribution** must ship with the wheel (CC-BY); LICENSE.txt next to the .shp.
- **Concurrency is 4** for DEM tiles (D-08) — not 1, not 8. Verified preference.

</specifics>

<deferred>
## Deferred Ideas

- **Sea / naval support** — bathymetry (e.g. GEBCO) + navigable sea regions. Coastline.geojson + DEM nodata already enable later land/sea distinction, but actual sea-floor depth data and "navy can sail here" semantics are out of scope for 2.1. Revisit before Phase 2.2 or as a new phase if naval gameplay becomes a v1 requirement.
- **User-drawn bbox / per-project bbox override** — for v1 the bbox is auto-derived from Wikidata country envelope (D-20). A canvas lasso or settings override could come later.
- **HydroSHEDS lv7/lv8** — finer basin granularity. lv6 is sufficient for condado/duchy clustering (Phase 2.2); finer levels could refine barony-level rivers later.
- **Per-step expandable log** (vs shared log panel) — D-27 chose shared; per-step history could be a polish item.
- **Preview slider** for ridge sensitivity — D-17 ships a 3-state slider with no live preview; live preview is post-v1.

</deferred>
