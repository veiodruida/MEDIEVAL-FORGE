Deliver LANDMASK-01 + LANDMASK-02 at FULL fidelity — the requirements deliberately
split out of Plan 08-14 to avoid silent scope reduction (per scope_reduction_prohibition).

Plan 08-14 only made the LayerTogglePanel landmask HEADER reachable (passed
projectId/branchId). It did NOT make the landmask polygon editable, because:
  - VertexEditLayer renders landmask (cyan) handles ONLY when `editableLayer='landmask'`
    (VertexEditLayer.tsx:787 gates barony handles on `!isLandmaskMode`).
  - There is NO store state that flips `editableLayer` baronies↔landmask.
  - VertexEditLayer's landmask path is wired (handleLandmaskDragEnd:739, localLandmaskCoords
    buffer, onLandmaskCoordsChange callback) but receives no `landmaskCoords` source and
    no `onLandmaskCoordsChange` from CanvasViewer.

This plan: add an `editableLayer` store toggle, surface it in the LayerTogglePanel, and
plumb landmask coords + the apply callback through CanvasViewer into VertexEditLayer.

**SCOPE FLAG (honesty over the frontend-only label):** LANDMASK-01 requires a SOURCE of
the current landmask polygon ring for the editor to seed handles. Today no clean
frontend artifact exposes it (the pipeline emits a `landmask` raster PNG + an ingest
`coastline.geojson`, not an editor-ready landmask ring). Task 1 resolves the source;
if it must add a thin READ-ONLY backend artifact endpoint (`landmask.geojson`), that is
ADDITIVE (no DAG/store-logic/parity change) and is acceptable for this deliverable even
though the GAP-A/B/C closure batch was frontend-only. The executor MUST first confirm
whether `coastline.geojson` (already produced by ingest) is usable as the landmask ring;
prefer reusing it over adding an endpoint.

Purpose: make the landmask actually editable in the running app (LANDMASK-01/02).
Output: editableLayer toggle + landmask coord plumbing + apply callback.
