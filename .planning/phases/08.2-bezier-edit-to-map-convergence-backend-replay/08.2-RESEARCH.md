## Summary

Phase 08.2 closes G8: a Bézier contour edit commits `op:'move'` and IS persisted to
`edit_events`, but the colored `BaronyLayer` and 12-file export never change. There are
exactly TWO missing wires, both now confirmed against the live code:

**Wire 1 — Replay gap in `manual_edit.compute()`** (lines 101-129): `op:'move'` /
`'add'` / `'delete'` ops silently fall through the replay loop. Only `'split'`,
`'merge'`, and `'translate'` are handled. The fix is NOT to add per-op helper functions
mirroring those three — the Bézier move op carries NO geometry in its persisted payload
(confirmed below). The correct approach is vertex-ring re-rasterisation from the
snapshot's `vertices` dict.

**Wire 2 — `_render_producer` never sets `cfg.manual_edit_log_hash` / `snapshot_loader`**:
confirmed by grep — zero occurrences of `snapshot_loader`, `manual_edit_log_hash`, or
`manual_edit_log_count` in `render.py` or `generate.py`. This was a known stub deferred
in 08-07c's "Known Stubs" table. So `compute()` always short-circuits to identity in
production regardless of whether vertex ops were stored. Wire 2 is the larger gap.

**Primary recommendation:** Re-rasterise affected barony rings from the snapshot's
`vertices` dict (geographic coords → pixel-space ring → `rasterio.features.rasterize`),
then wire `_render_producer` to read `branch.manual_edit_log_hash/count` from the DB
and inject a pre-fetched snapshot dict as `cfg.snapshot_loader` (mirroring the existing
`landmask_override` pattern at render.py lines 148-167).

**CRITICAL (four plan-blocking issues confirmed in research):**

1. **BLOCKING — `editLog` (camelCase) vs `edit_log` (snake_case) key mismatch.** Confirmed
   in `snapshots.ts` line 58: `snapshot_payload_if_due` uses `{ vertices, editLog }`.
   `compute()` line 77 reads `snapshot.get("edit_log", [])`. Every real snapshot blob has
   `editLog`, not `edit_log` → `compute()` gets `[]` → identity short-circuit → G8 persists
   after all other wiring. The Apply snapshot must send `edit_log` (snake_case), OR
   `compute()` must normalize with `snapshot.get("edit_log") or snapshot.get("editLog") or []`.
   [VERIFIED: snapshots.ts line 58, manual_edit.py line 77]

2. **`barony_name_to_idx` must be built backend-side from `bars[]`.** `bars` is in scope
   at the `manual_edit` call site in both orchestrators (line ~429 / ~646). Passing
   `{b["name"]: i for i, b in enumerate(bars)}` into `compute()` eliminates all frontend
   ordering assumptions (A2/A4). No need to embed this in the snapshot blob.

3. **Interior gaps are structural, not just shared-edge risk.** SelectionBridge loads one
   barony ring at a time. D-30 coupling updates partner vertices but not partner full rings.
   Re-rasterising baronX's updated ring while neighbours hold old vectorised polygons
   creates gaps (shrink) or overwrites (expand) on ALL interior boundaries. BEZ-CONV-05
   UAT must target a **coastline barony** (open boundary, no neighbours to gap) for the
   initial implementation. Interior shared edges are a follow-on design decision.

4. **Auto-immediate mode (D-01) needs a snapshot per cascade.** Each auto-immediate render
   must post a fresh snapshot (with `vertices` and `edit_log`) before triggering `/render`,
   not rely on the 25-edit auto-snapshot cadence.

## Research Target #1 (THE CRUX): Replay Geometry Source

### Confirmed: op:'move' payload carries NO geometry coordinates

Verified in `BezierEditLayer.tsx` `handleDragEnd` (lines ~565-572):

```typescript
// BezierEditLayer.tsx lines 565-572 — the actual commit
useEditorStore.getState().setVerticesAndLog(nextVertices, {
  op: 'move',
  ts: Date.now(),
  vertexIds: changedIds,
  // NOTE: NO lat/lon fields — only vertexIds
})
```

The raw `moveVertex` action in `useEditorStore.ts` (line ~202) DOES carry `lat/lon`,
but `BezierEditLayer` calls `setVerticesAndLog` directly with only `vertexIds`. The
`EditEventSink` fires this via `POST /edit-events` with `op_type: 'move'` and a payload
containing only `{ vertexIds: changedIds }`.

**Consequence:** Any plan to `replay_move(polygon, vertexId, lat, lon)` is blocked —
the payload has no coordinates. The only coordinate source is the `vertices` dict in the
snapshot blob. [VERIFIED: live code inspection]

### Confirmed: all three vertex ops reduce to one operation

`move`, `add`, and `delete` all produce the same observable effect in the snapshot
`vertices` dict: the dict after the ops reflects the final geometry. Re-rasterising the
ring from `snapshot["vertices"]` handles all three:
- `move`: vertex coord changed in dict
- `add`: new key `baronyId#N` inserted in dict
- `delete` / `multi_delete`: key(s) removed from dict

No per-op helper functions needed. One `replay_vertex_ring(barony_id, vertices_dict,
polygons_by_id, cfg)` helper replaces the conceptual three. [VERIFIED: code analysis,
confirmed by advisor] [CITED: karpathy-simplicity principle]

### The baronyId → raster index mapping

Confirmed from `canvas_sidecars.py` `build_baronies_geojson_sidecar` (lines 207-247):

```python
for bi, b in enumerate(bars):
    bname = b["name"]
    features.append({
        "id": bname,
        ...
    })
    colors[b["name"]] = idx_to_hex[bi]
```

And from `SelectionBridge.tsx` (lines 75-86):

```typescript
vertices[`${selectedBaronyId}#${i}`] = { lat, lon }
// where selectedBaronyId === b.id === b["name"] (the barony name string)
```

**The key mapping:** `baronyId` (frontend string key in `vertices`) = `b["name"]`
(the barony name string in `bars[bi]`) = raster value `bi` (integer index).

**To look up the raster index from baronyId in `compute()`:**
The `bars` list is NOT available inside `compute()` — it lives in `_VORONOI_CACHE`.
The snapshot dict (from `snapshot_loader`) contains `edit_log` and the frontend
`vertices` dict. The mapping from baronyId string → raster integer is the reverse of
the sidecar emit. The clean approach: the snapshot payload should include a
`barony_name_to_idx` mapping (built during Apply cascade), OR `compute()` must receive
the `bars` list.

**Recommended design:** Extend the snapshot payload convention OR pass the `bars`
lookup through `cfg`. Since `run_pipeline_incremental` already has `bars` in scope at
the `manual_edit` stage call, the cleanest approach is to build a `barony_name_to_idx`
dict and store it in the snapshot payload when the "Apply edits" snapshot fires.

**Alternative (simpler):** Store `barony_name_to_idx` in the snapshot's `vertices`
section implicitly — since `vertices` keys are already `"baronyId#N"`, `compute()` can
parse the baronyId from the key prefix (everything before `#`) and look it up from the
snapshot. But the snapshot blob (`SnapshotPayload`) only has `geojson`, `region_config`,
and `edit_log` fields — NOT `vertices`. [VERIFIED: snapshot.py lines 20-24]

**Critical discovery (advisor-confirmed):** The snapshot `SnapshotPayload` TypedDict
(snapshot.py lines 20-24) stores `{ geojson, region_config, edit_log }` — NOT the
frontend `vertices` dict. The `vertices` dict in `useEditorStore` is the *runtime
frontend state*, not stored in backend snapshots. The `edit_events` table only stores op
payloads (which carry no coordinates for move ops).

**Resolution:** The "Apply edits" button must POST a snapshot with extended payload
before triggering render. The snapshot payload needs to include `vertices` (the current
frontend geometry). The `snapshot_loader` on the backend then returns a dict that
includes `vertices`, and `compute()` reads the ring from it.

**The full geometry chain for replay:**
1. Frontend "Apply" button posts snapshot: `{ ..., vertices: { "baronX#0": {lat,lon}, ... } }`
2. `_render_producer` fetches this snapshot via `restore_snapshot(latest_snapshot_id)`
3. Injects a synchronous closure: `cfg.snapshot_loader = lambda branch_id: fetched_snapshot_payload`
4. `compute()` reads `snapshot["vertices"]` keyed by `baronyId#N` prefix
5. Parses baronyId from key, maps to raster index via `bars` list

Wait — `compute()` does not receive `bars`. Resolution: pass `bars` through a new
optional field on RegionConfig, OR have the snapshot payload include the `barony_name_to_idx`
mapping. The latter is simpler and doesn't change `RegionConfig`.

**Final recommended design (revised):** Build `barony_name_to_idx` BACKEND-SIDE
from the `bars` list that is already in scope at the `manual_edit` call site in both
`run_pipeline` and `run_pipeline_incremental` (~line 429 / ~line 646). Add an optional
`barony_name_to_idx: dict[str, int] | None = None` parameter to `compute()`. The
orchestrators pass `{b["name"]: i for i, b in enumerate(bars)}` directly. This eliminates
all frontend ordering assumptions (A2/A4) — the mapping derives from the authoritative
`bars` list, not from the GeoJSON feature order or territory_metadata array order.

[VERIFIED: snapshot.py TypedDict allows extra keys since Python TypedDicts are not strict by default]
[VERIFIED: code trace from canvas_sidecars.py + SelectionBridge.tsx]

### The coordinate transform: geo → raster pixel space

`compute()` uses `from_bounds(0, 0, W, H, W, H)` for the rasterio affine transform.
`geo_to_pixel()` in `contracts.py` (lines 176-187) converts lon/lat to pixel (px, py)
with these formulas:

```python
span = (cfg.lon_max - cfg.lon_min) * cfg.lon_scale
px = int((lon - cfg.lon_min) * cfg.lon_scale / span * W)
py = int((1.0 - (lat - cfg.lat_min) / (cfg.lat_max - cfg.lat_min)) * H)
```

The `from_bounds(0, 0, W, H, W, H)` affine has a y-flip (top-left origin, y increases
downward), which matches the Pillow/numpy convention. `geo_to_pixel` also produces
y-downward coords. Verified consistent. [VERIFIED: contracts.py lines 176-187]

**For replay:** given `vertices` dict entries `{lat, lon}`, call `geo_to_pixel(lon, lat, cfg)`
to get `(px, py)` and build a `Polygon` ring from the ordered vertex sequence. The ring
ordering is already stable: `sortRingKeys(keys)` sorts by numeric suffix, so
`baronyId#0`, `baronyId#1`, ..., `baronyId#N-1` is the correct winding order.

**Required round-trip identity test:** rasterise an unedited barony ring through the
new path and confirm the pixel mask matches the vectorised-from-raster polygon. This is
the single check that de-risks the coordinate-space assumption. [ASSUMED: round-trip
holds; must be verified empirically as Wave 0 of the plan]

```python
async with AsyncSessionLocal() as _db:
```

```python
                .where(Snapshot.branch_id == branch_id)
```

## Research Target #3: Shared-Boundary / Gap Consequence

### Shared-vertex coupling: what's actually in the store on Apply

`SelectionBridge.tsx` loads vertices for ONE barony at a time (line 62: `const b =
baronies.find((x) => x.id === selectedBaronyId)`). The loaded `vertices` dict contains
only keys `selectedBaronyId#N`. However, `BezierEditLayer.handleDragEnd` runs
`getCoupledVertices` for each changed vertex and adds coupled partner keys to
`nextVertices` (lines 553-564). So after a commit, `vertices` may contain:
- `baronX#0..#N-1` (the active barony)
- `baronY#3`, `baronY#7` (coupled neighbours if shared vertices were dragged)

**Gap risk:** When `compute()` re-rasterises `baronX` using its updated ring, the
neighbour `baronY`'s raster region is NOT re-rasterised (no `baronY` entry in the loop
unless explicitly handled). The `rasterize()` call uses `fill=-1`, so pixels vacated by
`baronX`'s ring shrink get filled with ocean sentinel, creating a visible gap.

**Mitigation:** When re-rasterising baronies from the snapshot vertices, iterate all
distinct barony prefixes in `vertices` (not just the changed ones). This naturally
handles coupled neighbours because their updated coordinates are already in `vertices`.

**Remaining gap risk after mitigation:** If the coupled neighbour's ring contains vertices
NOT in the snapshot `vertices` dict (because SelectionBridge only loaded one barony at a
time), the coupled vertices are updated but the full ring isn't available to re-rasterise.

**Verification task required:** Test a real Iberia barony move on a shared edge. Check
whether the snapshot `vertices` after coupling contains enough of the neighbour ring to
re-rasterise it correctly, or whether only the coupled points are present (leaving the
rest of the neighbour ring missing from the snapshot). This is a plan Wave 0 task.

**Safe conservative approach (plan should prescribe this):** When the snapshot
`vertices` dict contains keys from barony X and partial keys from barony Y (due to
coupling), only re-rasterise baronies for which ALL N ring vertices are present in the
snapshot. For baronies with only partial coverage (e.g., only the coupled vertices),
use the rasterio-vectorised polygon from the upstream `result` array and apply the
coupled vertex delta as a `replay_translate`-style point-edit. This avoids silently
creating gaps from an incomplete ring.

## Research Target #4: add/delete Emission Scope

### Confirmed: add/delete emit shape

From `useEditorStore.ts`:

```typescript
addVertex: (id, lat, lon) => {
    const next = { ...get().vertices, [id]: { lat, lon } };
    get().setVerticesAndLog(next, { op: 'add', ts: Date.now(), vertexIds: [id], lat, lon });
},

deleteVertices: (ids) => {
    const next = { ...get().vertices };
    ids.forEach((i) => delete next[i]);
    get().setVerticesAndLog(next, { op: 'multi_delete', ts: Date.now(), vertexIds: ids });
},
```

Unlike `BezierEditLayer`'s move op, the raw `addVertex`/`deleteVertices` DO carry
coordinates in the persisted payload (for `add`: `lat`, `lon` in the op object).
However, the `multi_delete` op does NOT carry coordinates.

**Key insight:** Since the replay mechanism uses the snapshot `vertices` dict (not the
individual op payloads), the coordinate presence or absence in the persisted op payload
is IRRELEVANT to replay. The snapshot `vertices` dict already reflects all applied ops.
[VERIFIED: useEditorStore.ts lines 205-213]

### Confirmed: op:'move' from BezierEditLayer vs raw moveVertex

- `BezierEditLayer.handleDragEnd` → `setVerticesAndLog(nextVertices, { op:'move', ts, vertexIds: changedIds })` — NO lat/lon in the op
- Raw `moveVertex()` in store → `setVerticesAndLog(next, { op:'move', ts, vertexIds:[id], lat, lon })` — HAS lat/lon

Both produce `op_type: 'move'` in `edit_events`. Replay via snapshot `vertices` dict
handles BOTH cases uniformly. [VERIFIED: BezierEditLayer.tsx lines 565-572, useEditorStore.ts lines 200-203]

## Research Target #5: Frontend Trigger Wiring

### useParameterStudioDispatch reuse (D-02)

`useParameterStudioDispatch` (hooks/useParameterStudioDispatch.ts) is a
`useDebouncedCallback` that:
1. Cancels any in-flight render via `postRenderCancel`
2. Posts `diff + stageView` to `/render`
3. Calls `useRunStore.getState().startRender(run_id)`
4. On `RENDER_BUSY`: bounded retry (3 retries / 1.5s window, per-projectId counter)

For "Apply edits" convergence, the caller simply invokes `dispatch.flush()` (bypasses
the 250ms debounce) after posting the snapshot. No modifications to the hook needed —
it already handles all race/cancel/retry states. [VERIFIED: useParameterStudioDispatch.ts lines 40-88]

**IMPORTANT: The dispatch computes `diffOverrides(values, lastRendered)` and skips if
empty.** A barony edit does NOT change any pipeline slider value, so `diff` will be
empty and the dispatch will no-op! The plan must handle this.

**Fix:** Either (a) pass a dummy override (e.g., a timestamp-scoped no-op field), or
(b) add a `forceRender?: boolean` param to the hook, or (c) implement a separate
`dispatchBezierApply(projectId, branchId)` function that calls `postRender` directly
without the diff check. Option (c) is the simplest and stays consistent with D-02
("no bespoke plumbing" means reusing `/render` endpoint and SSE path, not the diff-check
logic). [VERIFIED: useParameterStudioDispatch.ts lines 49-51]

### baroniesQ refetch location (BEZ-CONV-03)

`CanvasViewer.tsx` calls `useCanvasArtifacts(projectId, projection, effectiveCacheVersion, stageView)`.
The `effectiveCacheVersion` derives from `cacheVersion` prop (= `project.updated_at`).
After a successful render, `_render_producer` bumps `project.updated_at` in the DB
(render.py lines 183-190), so the next `project` query will return a new `cacheVersion`,
triggering all 5 `useCanvasArtifacts` queries to refetch — including `baroniesQ`.

The existing pattern already handles this: when the parent `WorkspaceDetail` or
`ProjectDetail` refetches `project`, the new `updated_at` propagates to `cacheVersion`
prop → `effectiveCacheVersion` changes → all canvas queries refetch.

**No additional `baroniesQ.refetch()` call needed** beyond the existing cacheVersion
invalidation that already fires after any render. [VERIFIED: render.py lines 183-190,
CanvasViewer.tsx lines 339-367]

**Overlay clear-on-converge:** `BezierEditLayer`'s amber-dashed overlay is driven by
`useMemo` over `vertices` (lines 826-838). After a successful render, the colored raster
updates BUT `vertices` in the store stays unchanged (Ctrl+Z reverts store, not map —
D-03 discretion). The overlay clears when `activeTerritoryId` is cleared (user
deselects) or when `editLog` is reset. A clean UX: clear `editLog` (and optionally
zundo history) after a successful "Apply edits" cascade, which sets `vertices` back to
the post-render state via a re-fetch. The plan should prescribe when/how the overlay
clears; research says the mechanism is `setActiveTerritoryId(null)` or
`useEditorStore.setState({ editLog: [] })`.

```python
# After the op loop — re-rasterise all baronies whose rings are in the snapshot
vertices_dict = snapshot.get("vertices", {})
barony_name_to_idx = snapshot.get("barony_name_to_idx", {})
if vertices_dict and barony_name_to_idx:
    # Group vertex keys by barony prefix
    barony_rings = {}
    for key, coord in vertices_dict.items():
        barony_name = key.split('#')[0]
        idx = barony_name_to_idx.get(barony_name)
        if idx is None:
            continue
        barony_rings.setdefault(idx, []).append((key, coord))
    for raster_idx, ring_entries in barony_rings.items():
        # Sort by numeric suffix (same as sortRingKeys in frontend)
        sorted_entries = sorted(
            ring_entries,
            key=lambda x: int(x[0].split('#')[1]) if '#' in x[0] else 0
        )
        pixel_coords = [
            geo_to_pixel(e[1]['lon'], e[1]['lat'], cfg)
            for e in sorted_entries
        ]
        if len(pixel_coords) < 3:
            continue
        edited_poly = Polygon(pixel_coords)
        if edited_poly.is_valid and not edited_poly.is_empty:
            polygons_by_id[raster_idx] = [edited_poly]
```

**Key point:** This must run AFTER the existing split/merge/translate loop, not instead
of it — a branch may have a mix of polygon ops and vertex ops in its edit log. For
vertex ops that precede a split/merge, the snapshot `vertices` at Apply time will
already reflect all ops up to that point.

### Anti-Patterns to Avoid

- **Do NOT add `replay_move(polygon, vertexId, lat, lon)` functions** mirroring split/merge/translate.
  The op payload has no coordinates for Bézier moves. Ring re-rasterisation from snapshot is the correct approach.
- **Do NOT vectorise the raster and try to remap vertex IDs.** `compute()` currently
  vectorises via `rasterio.features.shapes`, but those shapes have no stable vertex IDs —
  they're just ring coordinates. ID remapping to match the frontend store's vertex keys
  is not feasible.
- **Do NOT call `diffOverrides()` path in `useParameterStudioDispatch` for Apply edits.**
  `diff` will be empty (no slider changed), causing a silent no-op. Use a direct
  `postRender()` call.
- **Do NOT scope vertex-op replay by `op_type` in the edit_events filter.** The edit log
  contains a mix of polygon and vertex ops; replay them all together. Filtering by
  op_type would break branches that have split+move sequences.

## Common Pitfalls

### Pitfall 0 (BLOCKING): `editLog` camelCase vs `edit_log` snake_case mismatch

**What goes wrong:** `snapshots.ts` `EditEventPayload.snapshot_payload_if_due` uses
`{ vertices, editLog }` (camelCase — confirmed line 58). The backend stores this dict
verbatim in the snapshot blob. `compute()` calls `snapshot.get("edit_log", [])`.
Key `edit_log` is never present in any real frontend snapshot → `edit_log = []` →
`if not edit_log: return input_array` → G8 symptom persists after all wiring.
[VERIFIED: snapshots.ts line 58, manual_edit.py line 77]

**How to avoid (two options — planner picks one):**

Option A (preferred): Apply snapshot uses `edit_log` key explicitly:
```python
payload = { "vertices": vertices_dict, "edit_log": edit_log_list, ... }
```
This is the Apply-specific code path that owns the key name.

Option B (belt-and-suspenders): Normalize in `compute()`:
```python
edit_log = snapshot.get("edit_log") or snapshot.get("editLog") or []
```
This also fixes the 25-edit auto-snapshot path (which uses camelCase).

**Warning signs:** After all wiring, render runs (SSE events visible), but
`lookup_barony.png` is byte-equal to zero-edit baseline — `compute()` still returns
`input_array` unchanged.

### Pitfall 1: snapshot_loader lambda capturing None

**What goes wrong:** `cfg.snapshot_loader = lambda _: snapshot_data` — if `snapshot_data`
is a local variable in an `async with` block that has already exited, the closure
captures the reference which may be `None` at call time.

**How to avoid:** Capture by value: `cfg.snapshot_loader = lambda _bid, _d=snapshot_data: _d`
(Python default-arg capture idiom). [VERIFIED: Python closure semantics]

**Warning signs:** `compute()` logs `edit_log = []` despite the branch having edits.

### Pitfall 2: Incomplete ring → invalid Shapely polygon

**What goes wrong:** If `vertices` dict only contains coupled vertices (partial ring of
a neighbour barony), `Polygon(pixel_coords)` with 2-3 points creates a degenerate or
invalid polygon. Rasterization of an invalid polygon is silently skipped.

**How to avoid:** Guard `if len(pixel_coords) >= 3 and edited_poly.is_valid`. Only
re-rasterise baronies where the full ring is present (key count matches expected N from
the original vectorised polygon).

**Warning signs:** Neighbor barony disappears from `lookup_barony.png` after Apply.

### Pitfall 3: diffOverrides empty → no-op render dispatch

**What goes wrong:** Calling `dispatch.flush()` (or `dispatch()`) for "Apply edits" when
only barony vertex ops exist — no pipeline slider changed, `diff = {}`, early return at
line 51 of `useParameterStudioDispatch.ts`, render never fires.

**How to avoid:** Bypass `diffOverrides` and call `postRender(projectId, {}, stageView)`
directly for Apply edits. Handle `RENDER_BUSY` retry separately or reuse the counter.

**Warning signs:** No SSE stream events appear after clicking "Apply edits".

### Pitfall 4: BEZ-CONV-04 scope — parity break on landmask-only branches

**What goes wrong:** Wiring `cfg.manual_edit_log_hash` from the branch row whenever
`branch_row.manual_edit_log_hash` is non-empty — but a branch that has only
`landmask_replace` ops will also have a non-empty hash (because `/editor/apply`
bumps the hash for landmask ops too). This would force vertex-op replay on a
landmask-only branch, running `vectorise → rasterise` roundtrip that 08-07c
does NOT guarantee byte-equal for an empty vertex edit log.

**How to avoid:** In `compute()`, check specifically for vertex-op entries in the edit
log before entering the ring re-rasterisation path. If no vertex ops exist, skip the
ring re-rasterisation entirely (the existing split/merge/translate path still runs).
The identity short-circuit for `manual_edit_log_hash == ""` stays unchanged (D-05).

**Warning signs:** Iberia parity test fails on a landmask-only branch.

### Pitfall 5: `barony_name_to_idx` not in snapshot payload

**What goes wrong:** Frontend sends snapshot without `barony_name_to_idx` field.
`compute()` cannot map baronyId string to raster integer, silently skips all vertex ops.

**How to avoid:** Build `barony_name_to_idx` from `effectiveBaronies` data (already
loaded in CanvasViewer), include it in the snapshot payload on every Apply snapshot.

**Warning signs:** `compute()` runs (hash non-empty, loader non-None), but no pixels
change after Apply.

### Pitfall 6: coords in `from_bounds(0,0,W,H,W,H)` vs `geo_to_pixel` convention

**What goes wrong:** `from_bounds(0, 0, W, H, W, H)` in `compute()` uses rasterio's
affine with (col, row) = (x, y) in pixel space. `geo_to_pixel` returns `(px, py)` where
`py` is row (downward). These must align: `Polygon([(px0,py0), (px1,py1), ...])` where
`px` = column index and `py` = row index. The Shapely Polygon from `geo_to_pixel` coords
and the rasterio affine transform should be consistent.

**How to avoid:** Validate with the round-trip identity test: rasterise an unedited
barony ring → confirm pixel mask matches the original `result == bi` mask.

### replay_vertex_ring helper (backend)

```python
# Source: manual_edit.py (new helper function)
from shapely.geometry import Polygon
from .contracts import geo_to_pixel

def replay_vertex_ring(
    barony_name: str,
    barony_name_to_idx: dict[str, int],
    vertices_dict: dict[str, dict],
    polygons_by_id: dict[int, list],
    cfg,
) -> None:
    """Replace a barony's polygon with the ring from the snapshot vertices dict.

    This is a PURE FUNCTION — no DB access, no side effects.
    Called from compute() after the existing split/merge/translate loop.
    """
    raster_idx = barony_name_to_idx.get(barony_name)
    if raster_idx is None:
        return
    # Collect all keys for this barony, sorted by ring index
    ring_keys = sorted(
        [k for k in vertices_dict if k.startswith(barony_name + '#')],
        key=lambda x: int(x.split('#')[1]) if '#' in x else 0
    )
    if len(ring_keys) < 3:
        return
    pixel_coords = [
        geo_to_pixel(vertices_dict[k]['lon'], vertices_dict[k]['lat'], cfg)
        for k in ring_keys
    ]
    try:
        poly = Polygon(pixel_coords)
    except Exception:
        return
    if poly.is_valid and not poly.is_empty:
        polygons_by_id[raster_idx] = [poly]
```
