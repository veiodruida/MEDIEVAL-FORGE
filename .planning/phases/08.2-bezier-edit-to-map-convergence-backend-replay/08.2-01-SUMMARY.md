## Decisions Made

### A1 Coordinate Contract (Critical Discovery)

The round-trip identity test required a significant coordinate investigation. Key findings:

1. **`rasterio.features.shapes` with `from_bounds(0,0,W,H,W,H)`** returns polygon vertices in rasterio world space where `y=0` is bottom and `y=H` is top (south-up convention).

2. **`_ring_to_lonlat` in canvas_sidecars.py** treats the rasterio `y` coordinate correctly — its formula `lat = lat_max - y/H * (lat_max - lat_min)` is calibrated to rasterio world y (not pixel row index).

3. **`geo_to_pixel`** returns `py_row` where row 0 = top (y grows DOWN, opposite convention). Uses `int()` truncation.

4. **Round-trip conversion for rasterize**: to convert lon/lat back to rasterio world y:
   - `py_row = round((1 - (lat - lat_min)/(lat_max - lat_min)) * H)` (NOT `int()`)
   - `rasterio_y = H - py_row`
   - Using `int()` instead of `round()` causes ~34px drift per barony ring (13% of barony area for a 265-pixel barony).

5. **Verification**: `round() + H-flip → 0 diff pixels` (byte-equal); `int() + H-flip → 34 diff pixels`.

**Plan 02 contract**: `replay_vertex_ring()` must implement its own rounding helper. `geo_to_pixel` is parity-frozen and MUST NOT be modified.

**1. [Rule 1 - Bug] Fixed coordinate convention in _lonlat_to_rasterio_xy helper**
- **Found during:** Task 1 GROUP A implementation
- **Issue:** Initial implementation of `_lonlat_to_rasterio_xy` computed `rasterio_y = (lat_max - lat) * H / (lat_max - lat_min)` which is pixel row index (0=top), not rasterio world y (0=bottom).
