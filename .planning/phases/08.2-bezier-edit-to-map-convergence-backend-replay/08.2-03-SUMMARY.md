## Decisions Made

### BezierApplyControls Extraction

WorkspaceToolbar was 228 LOC before this plan. Adding the Apply Edits control group inline would exceed the ~250 LOC planner-stated budget (UI-SPEC §New Files note explicitly permits extraction). The controls were extracted into `BezierApplyControls.tsx` with the data-testids referenced by the acceptance criteria (`bezier-apply-edits-btn`, `bezier-apply-auto-switch`) — the criteria allow the subcomponent to host the anchors.

### pendingApplyRef Guard

The useRunStore subscription in `useBezierApply` uses a `pendingApplyRef` flag that is set to `true` only after a successful snapshot POST and `postRender` call. This prevents an unrelated parameter-studio render (which also transitions `rendering → generated`) from clearing a user's in-progress Bézier edits. The ref is reset on both success and error paths.

### vi.clearAllMocks() + Mock Return Value

`vi.clearAllMocks()` in `beforeEach` clears mock implementations, including the `postRender` factory return. Fix: re-register `vi.mocked(postRender).mockResolvedValue(...)` in `beforeEach` after `clearAllMocks`. This is standard vitest pattern with module-level `vi.mock`.

The overlay guard now passes (non-empty editLog = pending edits = overlay visible, which is what the existing tests expected before this plan's semantic change).

### editLog: grep gate returns 2, not 0 (verifier note)

Task 2 acceptance criteria: `grep -c "editLog:" → 0`. The hook returns 2 hits:
1. A JSDoc comment (`temporal.pause(); useEditorStore.setState({ editLog: [] })`) — documentation only.
2. Line 145: `useEditorStore.setState({ editLog: [] })` — this is the spec-mandated clear-on-converge reset (UI-SPEC Note 8). It uses `editLog:` as a store key, NOT as a POST payload key. The criterion targeted camelCase `editLog:` appearing in the snapshot POST body; the actual POST uses `edit_log:` (snake_case). Both occurrences are correct and required.

### UI-SPEC Note 9 / Playwright spec status

The `08.1-bezier-render-feedback.spec.ts` Describe 2 migration (UI-SPEC §104-114, Note 9) was already applied **before this plan** — the spec was already updated to the "drag-first, then assert overlay" pattern (lines 290-298 confirm this). The vitest unit test MockState fix in `BezierEditLayer.test.tsx` + `drag.test.tsx` is a separate required change (the mock did not include `editLog`, causing TypeError on the new guard) — it is NOT the Note 9 playwright migration. The playwright spec is compatible with the `editLog.length > 0` guard because `editedContourPointCount` reads from `editedRingPtsRef.current` (a ref synced unconditionally every render), not from the overlay element's presence.

## Known Stubs

**Auto-immediate mode is incomplete (deferred to Plan 04):**
- `useBezierApply.triggerAutoApply` is defined and tested in isolation but is NOT wired to any trigger in the app. Nothing calls it after `setVerticesAndLog`.
- A user who toggles "Auto-aplicar" ON will see the orange badge and the Apply button will be hidden — but no convergence cascade will fire automatically after each edit.
- **Wire path** (Plan 04): subscribe to `editLog` growth in `BezierApplyControls` or in a `useEffect` in the hook; call `triggerAutoApply` when `bezierApplyMode === 'auto-immediate'` and `editLog.length` increases. Guard: the `editLog = []` reset in the success callback must NOT re-trigger (compare length, not identity).
- BEZ-CONV-05 Playwright spec should NOT test auto-immediate convergence until Plan 04 wires it.

Manual Apply flow is fully wired end-to-end:
- `useBezierApply.handleApplyEdits` POSTs to the real snapshots endpoint and calls the real `postRender` from `api/render.ts`.
- The `useRunStore.subscribe` transition fires on the real RunStore state machine.
- `temporal.pause → setState({editLog:[]}) → temporal.resume` is the real zundo API.
