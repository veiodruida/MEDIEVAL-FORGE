## Decisions Made

- Spec collapsed two sequential Apply calls into one honest Apply-once flow: running two Apply calls in the same test caused raster-collision (second raster was nearly identical to first, SHA-poll gave false negative). One drag + one Apply is the correct single-test footprint.
- SHA-poll pattern (capture `lookup_barony.png` SHA before drag, assert SHA differs after Apply) chosen over pixel-region diff — more stable across render timing variance and server restart states.
- Export assertion uses SHA diff against zero-edit baseline captured at spec start — feasible without unzipping the export ZIP.

## Open Issues (Deferred — Out of Scope for this Plan)

### KNOWN DEFECT: replay_vertex_ring degrades edited barony after MULTIPLE renders

- **Symptom:** Gijón disappears from `baronies.geojson` and `territory_metadata.json` on the SECOND replay after Apply. Pixels remain in the raster (visible in browser), but `rasterio.features.shapes` does not extract the polygon on re-render.
- **Root cause (suspected):** `buffer(0)` on the edited ring returns a `MultiPolygon` in some non-convex cases. The sidecar writer only iterates the outermost polygon of a `Polygon`; `MultiPolygon` parts are silently skipped, causing the barony to vanish from the GeoJSON on the second raster pass.
- **Impact:** Single Apply is intact (G8 fully closed for the first edit). The defect only manifests on a second Apply to the same barony in the same session/branch.
- **Triage:** Needs a targeted fix in `backend/medieval_forge/services/pipeline/replay.py` — iterate `geom.geoms` if `geom.geom_type == 'MultiPolygon'` and take the largest part, or union all parts before passing to the sidecar.
- **Follow-up:** Create a dedicated bug plan or quick-task for this before Phase 08.2 is closed.
