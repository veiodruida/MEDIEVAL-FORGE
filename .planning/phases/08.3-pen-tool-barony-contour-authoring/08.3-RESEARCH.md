# Phase 08.3: Pen Tool — Barony Contour Authoring — Research

**Researched:** 2026-05-30
**Domain:** Frontend pen-draw state machine (Konva) + backend CREATE convergence (pipeline DAG extension)
**Confidence:** HIGH — all six research targets answered with file:line evidence from live code

---

## Summary

Phase 08.3 adds a Photoshop-style pen tool (click=straight anchor, click-drag=curve handle) to the
canvas. Two capabilities: CREATE a brand-new barony in a gap, EXTEND an existing contour. The phase
explicitly reuses the Phase 08.2 replay/cascade machinery rather than inventing a parallel path.

The research confirms the **core asymmetry** from CONTEXT.md: EXTEND is close to free (existing
`replay_vertex_ring` path + new UI gesture); CREATE requires genuine new backend work. The hardest
finding is a **hierarchy coverage gap** that affects both CREATE and the existing split path: any
`allocated_original_idx` value ≥ `nb` (len(bars) from setup_baronies) is silently skipped by
`build_hierarchy_maps`, `generate_lookup_map`, and `export_metadata`, so a naively rasterised
CREATE barony produces pixels in the raster but zero condado assignment, no RGB in
`lookup_barony.png`, and no entry in `territory_metadata.json`.

**Primary recommendation:** Implement CREATE as a two-phase mechanism: (1) insert the drawn ring as
an extended `bars[]` entry with an allocated `original_idx` and D-08/D-09 country+condado
assignment BEFORE the manual_edit stage hands off to hierarchy, so `nb`, `bc`, `bd`, `bk` all
cover the new idx; (2) in `manual_edit.compute()`, rasterise the ring into the int16 grid at that
idx. This keeps the existing `build_hierarchy_maps`, `generate_lookup_map`, and `export_metadata`
functions unmodified while making CREATE fully convergent.

## Research Target Findings

### Target 1 — CREATE Convergence (THE CRUX)

**Question:** How does a new closed ring enter `manual_edit.compute()` and get rasterised into the
int16 grid with a server-allocated `original_idx`?

**Evidence — the existing replay loop** (`manual_edit.py` lines 147-193):

```
for op in edit_log:
    op_type = op["op"]
    if op_type == "split":   ...
    elif op_type == "merge": ...
    elif op_type == "translate": ...
    # vertex ops (move/add/delete/multi_delete) → ring re-rasterisation (lines 187-193)
```

A new `op_type == "create"` carries `ring: [{lat, lon}, ...]` and `allocated_original_idx: int`.
Adding a branch here is mechanically clean — the pattern is already established.

**The rasterisation itself** is already implemented in `replay_vertex_ring` (lines 327-399). CREATE
can reuse `_lonlat_to_rasterio_xy` (lines 48-63) and the Shapely `Polygon(pixel_coords)` →
`buffer(0)` → `largest-component` guard (lines 376-394) to build the ring poly, then assign it to
`polygons_by_id[allocated_original_idx]`.

**THE CRITICAL HIERARCHY GAP — confirmed by orchestrator trace:**

```python
# __init__.py line 440 (full pipeline) and line 667 (incremental):
pc, pd, pk = build_hierarchy_maps(result, bc, bd, bk, nb)
```

`build_hierarchy_maps` (voronoi.py lines 143-160):
```python
for bi in range(nb):   # nb = len(bars) built from cfg.condados at setup_baronies
    m = result == bi
    ...
```

`nb` is fixed at Voronoi time from `cfg.condados`. An `allocated_original_idx` ≥ `nb` is silently
skipped. The CREATE barony's pixels have the right raster value, but:
- `pc[those_pixels] == -1` (no condado assignment)
- `generate_lookup_map(..., n_items=nb, ...)` does not iterate the CREATE idx → no RGB in
  `lookup_barony.png`
- `export_metadata(... bars ...)` loops `enumerate(bars)` — CREATE barony has no `bars[i]` entry

**This also applies to split children.** `allocate_next_original_idx` returns `original_idx_high_water + 1`
(service.py line 204) which is ≥ nb. The split path paints the child at that idx, but
`build_hierarchy_maps` misses it too. Split UATs passed because the canvas sidecar
(baronies.geojson) carried the geometry from the prior full run, masking the hierarchy gap.

**Correct fix:** Extend `bars[]`, `bc`, `bd`, `bk`, and `nb` before `build_hierarchy_maps` runs.
This requires passing CREATE metadata through the manual_edit stage output or injecting it into the
orchestrator. The cleanest design: the `create` op payload carries `country` (from D-08) and
`condado_idx` (from D-09) so `manual_edit.compute()` can build the extended arrays and return them
alongside the modified raster. The orchestrator then passes the extended `bars/bc/bd/bk/nb` to
`build_hierarchy_maps`.

**Coordinate transform reuse:** `_lonlat_to_rasterio_xy` (manual_edit.py:48-63) is already defined
in this module and uses `round()` + rasterio y-flip (the A1 contract). CREATE uses it directly —
no new transform function needed. [VERIFIED: manual_edit.py lines 48-63]

**Recommended implementation:**

New branch in `manual_edit.compute()`:
```python
elif op_type == "create":
    ring_coords = op["ring"]   # [{lat, lon}, ...]
    new_idx = int(op["allocated_original_idx"])
    pixel_coords = [_lonlat_to_rasterio_xy(p["lon"], p["lat"], cfg, W, H) for p in ring_coords]
    # clip op["clip_geometry"] (neighbour difference — D-07) before rasterising
    # → same buffer(0) + largest-component guard as replay_vertex_ring (lines 376-394)
    poly = Polygon(pixel_coords)
    if not poly.is_valid:
        poly = poly.buffer(0)
        if isinstance(poly, MultiPolygon):
            poly = max((g for g in poly.geoms if g.area > 0), key=lambda g: g.area, default=None)
    if poly and not poly.is_empty:
        polygons_by_id[new_idx] = [poly]
        new_barony_meta.append(op["barony_meta"])  # {name, condado_idx, duchy_id, kingdom_id}
    _geometry_modified = True
```

`compute()` must return `(out_array, extended_bars_meta)` where `extended_bars_meta` lists any new
CREATE entries. The orchestrator uses them to extend `bars/bc/bd/bk` before calling
`build_hierarchy_maps`.

**Smallest viable change:** modify `compute()` return type from `np.ndarray` to
`tuple[np.ndarray, list[dict]]`; add a single new branch in the replay loop; update both
orchestrator call sites (~line 430 and ~line 654) to unpack the extended meta and extend arrays.
Two new files: none. Modified files: `manual_edit.py`, `__init__.py` (both call sites).

### Target 2 — `original_idx` Allocator Parentage (gates D-10)

**Question:** Does `allocate_next_original_idx` assume an existing parent?

**Evidence** (`service.py` lines 192-208):
```python
async def allocate_next_original_idx(db: AsyncSession, branch_id: str) -> int:
    branch = (await db.execute(select(Branch).where(Branch.id == branch_id))).scalar_one()
    branch.original_idx_high_water += 1
    new_idx = branch.original_idx_high_water
    await db.commit()
    ...
    return new_idx
```

**Finding:** The allocator is entirely parentless. It takes only `branch_id` — no parent barony id,
no country, no condado. It is a pure monotonic counter. **D-10 transfers as-is.**

The split path in `editor.py` calls it at line 254:
```python
elif body.op_type == "split":
    allocated_original_idx = await allocate_next_original_idx(db, body.branch_id)
```

There is no parent-dependent logic in the allocation itself. Country/condado for split are inherited
by the frontend (D-07/D-09) in the optimistic preview and embedded in the `create` op payload —
they are not derived from the allocator.

**CREATE needs a new `op_type == 'create'` handler in `editor.py`** that:
1. Calls `allocate_next_original_idx(db, body.branch_id)` (same as split)
2. Accepts `country` + `condado_idx` in the payload (for D-08/D-09 assignment)
3. Persists the op (ring coords + allocated idx + barony_meta) to `edit_events`
4. Returns `{allocated_original_idx, ...}` in the same `ApplyOpResponse` shape

The `op_type` regex on line 145 (`r"^(split|merge|translate|landmask_replace)$"`) needs `create`
added. [VERIFIED: editor.py lines 134-165]

**No parentage dependency.** D-10 is clear. [VERIFIED: service.py lines 192-208]

### Target 3 — Fixed Hand-Drawn Cell vs Voronoi (gates D-11)

**Question:** How to insert the drawn ring as a fixed KD-tree anchor without Voronoi/cleanup
redrawing it?

**Finding — D-11's stated mechanism does not match the architecture.** The CONTEXT.md text "insert
the drawn ring as a fixed KD-tree anchor so municipalities re-route to it" describes a Voronoi-time
action. But `manual_edit` runs **between merge and hierarchy** in the DAG
(`__init__.py` line 424: `# Phase 08 D-17 / BLOCKER-1 fix: manual_edit stage`), which is
**downstream of Voronoi, cleanup (apply_median, remove_fragments, smooth_per_territory), and
merge_small_blobs**. Those stages are cached and do NOT re-run on a barony-edit cascade.

The real mechanism for D-11 is:
- Voronoi, cleanup, and merge run on `cfg.condados` (the static territory data). The CREATE barony
  does not exist in `cfg.condados`. These stages produce the baseline raster.
- `manual_edit.compute()` receives the merged raster and **overpaints** it: rasterising the CREATE
  ring at `allocated_original_idx` overwrites whatever Voronoi painted there.
- Since Voronoi/cleanup/merge are cached, they don't re-run and cannot "merge away" the CREATE cell.
  The overpaint is permanent for this cascade.

**The >200px `blob_merge_px` threat is structurally moot** for convergence. `merge_small_blobs`
already ran upstream (cached). The 200px guard in D-17 is pure UX validation (client-side, before
commit) — it prevents committing a ring that would be invisible if the stage ran again. **The guard
is still needed as client-side validation** to give honest feedback, but it is not a structural
pipeline constraint for CREATE. [VERIFIED: cleanup.py lines 119-138, contracts.py line 91:
`blob_merge_px: int = 200`]

**Implication for the plan:** D-11 should be re-described as "raster overpaint in manual_edit, not
KD-tree mutation" — the practical effect is the same (hand-drawn ring is fixed and stable) but the
mechanism is different. No new KD-tree code is needed. This simplifies implementation.

### Target 4 — Clip Mechanism for Overlap (D-07)

**Question:** Does CREATE's clip reuse the existing Shapely boolean-op path, and can it reopen
the 08.2-05 MultiPolygon defect?

**Finding:** The clip is a `polygon.difference(union_of_neighbours)` call — standard Shapely. No
specialized function exists for this yet; the split/merge paths use `replay_split`/`replay_merge`
which are topologically different operations. CREATE's clip is new code but trivially implements:

```python
from shapely.ops import unary_union
neighbours_union = unary_union([poly for idx, polys in polygons_by_id.items()
                                for poly in polys
                                if idx != new_idx and poly is not None])
clipped = poly.difference(neighbours_union)
```

**MultiPolygon risk and the 08.2-05 guard:** `difference()` can produce a `MultiPolygon` if the
clip fragments the ring (e.g., a neighbor island in the middle). The same largest-component guard
that was added in 08.2-05 (`replay_vertex_ring` lines 388-394) MUST be applied identically here:

```python
if isinstance(clipped, MultiPolygon):
    parts = [g for g in clipped.geoms if g.area > 0]
    clipped = max(parts, key=lambda g: g.area) if parts else None
```

Applying this guard before assigning `polygons_by_id[new_idx]` makes the 08.2-05 defect structurally
impossible for CREATE. [VERIFIED: manual_edit.py lines 386-394]

**Note on sentinel safety:** After clipping, the rasterize step uses `fill=-1` (ocean sentinel).
The `out[ocean_mask] = -1` and `out[ignore_mask] = 9999` restore logic (lines 224-227) handles the
sentinels. CREATE rasterisation reuses the same path — no new sentinel risk.

### Target 5 — EXTEND Graft Mechanics (D-06)

**Question:** How does a 2-end-snapped open path map to existing ops?

**Finding: EXTEND is ~90% existing machinery.** The only new thing is the entry gesture.

The EXTEND path:
1. User draws an open path from snap-point-A to snap-point-B on the same barony's contour.
2. The path replaces the contour arc between A and B.
3. In store terms: the new vertices for the arc between A and B replace the old vertices.
4. This is a sequence of `op:'move'` and `op:'add'` ops on the barony's vertex ring.

`replay_vertex_ring` (`manual_edit.py` lines 327-399) rebuilds the ENTIRE ring from
`snapshot.vertices` — it doesn't care about individual op types, only the final vertex state.
**The existing machinery handles EXTEND correctly with zero changes** if the frontend writes the
updated vertices to `useEditorStore.vertices` and fires the standard `op:'move'/'add'` ops.

**The only new code is in the frontend:**
- `PenDrawLayer` detects EXTEND mode (first anchor snaps to an existing contour vertex/edge).
- On path close, it grafts the drawn arc into the existing vertex sequence: identify the indices
  of the two contact points in the store's `vertices` dict, replace the arc between them with the
  drawn vertices, then call `setVerticesAndLog` with the updated vertices and an appropriate op.

There is no new `op:'extend'` type needed. The store sees standard vertex mutations. The backend
replay path (`replay_vertex_ring`) handles it identically to a drag-move session.

**EXTEND also avoids the hierarchy gap** — the barony already exists in `bars[]` with a valid
`condado_idx`, so `build_hierarchy_maps` covers it in `range(nb)` without any extension needed.

## Architecture Patterns

### CREATE Op Flow (End-to-End)

```
PenDrawLayer (component-local)
  draw anchors → flat ring lat/lon
  → validate (D-17: ≥3 pts, no self-intersect, area ≥ 200px, ends snapped for EXTEND)
  → setVerticesAndLog({op:'create', ring, allocated_original_idx:null, barony_meta})
  → POST /editor/apply (op_type:'create', payload:{ring, barony_meta, branch_id})
  → backend allocates original_idx via allocate_next_original_idx
  → response: {allocated_original_idx, new_hash, new_count, ...}
  → patch editLog[-1].allocated_original_idx (mirror of split, lines 279-289)

On "Aplicar edições":
  → POST /render → _render_producer reads branch, injects snapshot_loader
  → run_pipeline_incremental:
      manual_edit dirty? YES
      → manual_edit.compute(result, cfg, barony_name_to_idx)
          create branch: rasterise ring at allocated_original_idx into polygons_by_id
          return (modified_raster, [barony_extension_meta])   ← NEW return shape
      → orchestrator extends bars/bc/bd/bk/nb with new entry
      → build_hierarchy_maps(result, bc, bd, bk, nb_extended)   ← covers CREATE idx
      → _write_outputs_to_disk(... extended bars/nb ...)
      → baroniesQ.refetch() → BaronyLayer colored
```

### EXTEND Op Flow

```
PenDrawLayer detects EXTEND (first anchor snapped to existing contour)
  → draw open path → snap second end to contour
  → graft arc into store.vertices (replace contour arc between contact points)
  → setVerticesAndLog({op:'move'/'add', ...}) — standard vertex ops
  → same path as Phase 08.2 replay_vertex_ring — no new backend op
```

### Anti-Patterns to Avoid

- **Do NOT put in-progress draw state (anchors, cursorPos) in `useEditorStore`** — component-local
  only, mirrors BezierEditLayer. [VERIFIED: BezierEditLayer.tsx lines 17-22]
- **Do NOT skip the largest-component guard on clip** — reopens 08.2-05 defect.
  [VERIFIED: manual_edit.py lines 386-394]
- **Do NOT call `build_hierarchy_maps` with the old `nb`** — silently produces ocean condado pixels
  for the CREATE barony. The orchestrator must extend arrays before this call.

## Common Pitfalls

### Pitfall 1: Hierarchy Coverage Gap (THE CRUX)
**What goes wrong:** CREATE barony rasterised at `allocated_original_idx` ≥ `nb`. Pixels appear
in raster. `build_hierarchy_maps` loops `range(nb)` — CREATE idx skipped. `pc[CREATE pixels] == -1`.
`lookup_barony.png` shows ocean color. `territory_metadata.json` missing the barony.
**Why it happens:** `nb = len(bars)` from `setup_baronies` which builds from `cfg.condados`. CREATE
barony is not in `cfg.condados`.
**How to avoid:** `manual_edit.compute()` returns `(array, [new_barony_meta])`. Orchestrator extends
`bars/bc/bd/bk/nb` before calling `build_hierarchy_maps`. This is 10-15 lines in `__init__.py`.
**Warning signs:** New barony appears in `baronies.geojson` sidecar (visible on canvas) but not
in `lookup_barony.png` (ocean color) or `territory_metadata.json` (missing entry).

### Pitfall 2: `geo_to_pixel` vs `_lonlat_to_rasterio_xy`
**What goes wrong:** Using `geo_to_pixel` (contracts.py, `int()` truncation) for CREATE ring gives
~34px drift. Ring rasterises in wrong position.
**Why it happens:** `geo_to_pixel` is parity-frozen (`int()` from inicio). `_lonlat_to_rasterio_xy`
uses `round()` + rasterio y-flip (A1 contract from 08.2).
**How to avoid:** Always use `_lonlat_to_rasterio_xy` for any ring that passes through
`manual_edit.compute()`. Never touch `geo_to_pixel`.

### Pitfall 3: MultiPolygon from clip reopens 08.2-05
**What goes wrong:** `poly.difference(neighbours_union)` returns a `MultiPolygon`. The sub-polygons
get separate rasterize entries, potentially at wrong idx values. Second Apply breaks `original_idx`.
**Why it happens:** Clip can fragment the ring if a neighbor is an island in the middle.
**How to avoid:** Same largest-component guard as `replay_vertex_ring` lines 388-394.

### Pitfall 4: Mid-draw Ctrl+Z fires store undo
**What goes wrong:** Ctrl+Z during draw pops the zundo stack instead of removing the last anchor.
**Why it happens:** `useKeyboardShortcuts` handles Ctrl+Z globally → calls `temporal.undo()`.
**How to avoid:** `PenDrawLayer` must intercept Ctrl+Z when `isDrawing=true` (via `keydown` on the
Konva stage or a React `useEffect` on the window) and call its local `removeLastAnchor` before the
global handler fires. Set `event.stopPropagation()` or use a priority-ordered key handler.

### Pitfall 5: Edge snap missing from `snapToNeighbour`
**What goes wrong:** D-05 requires snapping to both vertices AND edges of neighbors.
`snapToNeighbour` (snap.ts) only snaps to vertices (point candidates). Edge snap is absent.
**Why it happens:** The existing snap utility is vertex-only.
**How to avoid:** Add `snapToEdge(cursor, geojsonFeatures, stageScale)` to `snap.ts`. Find the
nearest point on any edge within 12px. Return `{lat, lon, edgeEndpointIds: [id1, id2]}` so
`PenDrawLayer` can also highlight the snapped edge segment.

### Pitfall 6: `allocated_original_idx: null` in the `create` op at store commit time
**What goes wrong:** The `create` op is committed to `editLog` with `allocated_original_idx: null`.
The Apply backend uses `op["allocated_original_idx"]` to rasterise. If the patch from the server
response fails to apply, the backend gets `null` and crashes.
**Why it happens:** Race condition or error in the post-close store patch.
**How to avoid:** Apply must read `allocated_original_idx` from the *persisted* `edit_events` row
(which was stored with the non-null value when `/editor/apply` created the event), not from the
frontend's potentially-null snapshot. The backend's `edit_events` table always holds the correct
allocated idx. The `snapshot_loader` retrieves `edit_log` from the snapshot blob; the snapshot is
written when `/render` is triggered, after the patch has applied.

```python
elif op_type == "create":
    new_idx = int(op["allocated_original_idx"])
    ring_coords = op.get("ring", [])   # [{lat, lon}, ...]
    if len(ring_coords) < 3:
        continue
    pixel_coords = [
        _lonlat_to_rasterio_xy(p["lon"], p["lat"], cfg, W, H)
        for p in ring_coords
    ]
    try:
        poly = Polygon(pixel_coords)
        if not poly.is_valid:
            poly = poly.buffer(0)
            if isinstance(poly, MultiPolygon):
                parts = [g for g in poly.geoms if g.area > 0]
                if not parts:
                    continue
                poly = max(parts, key=lambda g: g.area)
        # D-07: clip against all existing neighbours
        if polygons_by_id:
            neighbours_union = unary_union([
                p for idx, polys in polygons_by_id.items()
                for p in polys
                if p is not None and idx != new_idx
            ])
            if not neighbours_union.is_empty:
                poly = poly.difference(neighbours_union)
                if isinstance(poly, MultiPolygon):
                    parts = [g for g in poly.geoms if g.area > 0]
                    poly = max(parts, key=lambda g: g.area) if parts else None
        if poly and not poly.is_empty and poly.area > 0:
            polygons_by_id[new_idx] = [poly]
            new_barony_meta.append(op.get("barony_meta", {}))
    except Exception:
        continue
    _geometry_modified = True
```
