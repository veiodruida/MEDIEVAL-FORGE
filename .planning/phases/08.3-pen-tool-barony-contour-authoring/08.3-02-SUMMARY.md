# Phase 08.3 Plan 02: Barony Hierarchy Fields in Sidecar Summary

**One-liner:** Extended baronies.geojson Feature properties with `condado_idx` (int) + `duchy_id` + `kingdom_id` (str) via `cfg.duchies` lookup, and extended `BaronyFeature` TS interface with three optional fields so PEN-ASSIGN-01 (pen tool hierarchy inherit) is unblocked.

## What Was Built

**Backend (`canvas_sidecars.py`):** The barony emitter loop (`build_baronies_geojson_sidecar`, ~207-236) now derives `duchy_id` from `cfg.condados[condado_idx][4]` and `kingdom_id` from `cfg.duchies[duchy_id][0]` — the same derivation the condado emitter uses. Both are guarded: `duchy_id` defaults to `""` if `condado_idx` is out of range, `kingdom_id` defaults to `""` if `duchy_id` not in `cfg.duchies`. The `properties` dict now includes `condado_idx`, `duchy_id`, `kingdom_id` alongside the existing `id`, `name`, `condado_id`, `centroid`, `pixel_count`.

**Backend tests (`test_canvas_sidecars_hierarchy.py`):** 6 unit tests with a minimal `RegionConfig` fixture (2 baronies, 1 condado, 1 duchy, 1 kingdom, 10×10 raster). Covers: all three new fields present, correct values for duchy/kingdom, regression guard on existing fields, out-of-range condado_idx guard (empty strings returned safely).

**Frontend (`useCanvasArtifacts.ts`):** `BaronyFeature.properties` extended with `condado_idx?: number`, `duchy_id?: string`, `kingdom_id?: string` — all optional (old artifacts on disk pre-08.3 lack them; mirrors `centroid?` pattern from Phase 04.1).

**Frontend tests (`useCanvasArtifacts.hierarchy.test.ts`):** 7 vitest cases covering type compile, runtime value read-through, backward compat (Feature without hierarchy fields still valid), and type assertions on all three fields.
