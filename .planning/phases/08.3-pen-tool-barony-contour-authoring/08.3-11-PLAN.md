<architecture_facts>
EVIDENCE THAT SETTLES THE BACKEND QUESTION — NO BACKEND CHANGE IS NEEDED.

FACT 1 — Apply replays from the IN-MEMORY editLog's op.ring, not the close-time POST.
  useBezierApply.ts:runApply (lines 102, 117-125) builds the manual snapshot body with
  `edit_log: editLog` read from `useEditorStore.getState()` AT APPLY TIME, then POSTs it and
  calls postRender. backend/.../manual_edit.py:compute() loads that snapshot via
  cfg.snapshot_loader and rasterises CREATE (lines 200-247) and CARVE (lines 248-315) directly
  from `op["ring"]`. Therefore: if op.ring is mutated in the in-memory editLog before Apply,
  the snapshot carries the mutated ring and compute() rasterises the MANIPULATED shape. The
  /editor/apply POST fired earlier inside commitCreate (PenDrawLayer.tsx:751-796) only bumps
  hash/count + allocates original_idx — it does NOT freeze the geometry used by recompute.

FACT 2 — This mechanism is already proven by the carve-enclave-edit fix shipped THIS session.
  That fix edits an enclave's geometry AFTER close (through the vertices dict) and Apply honors
  it — proving the Apply-time snapshot overrides the close-time persisted op. A mutated op.ring
  in the same snapshot is honored by the identical mechanism. The backend question is retired.

FACT 3 — Single source of truth = op.ring; emit ZERO vertex ops.
  manual_edit.py:124,350 gates replay_vertex_ring behind `vertex_ops_present` (any op.op in
  {move,add,delete,multi_delete}). If we mutate op.ring and emit NO vertex op, vertex_ops_present
  stays FALSE → compute() rasterises purely from op.ring (the enrichVerticesFromEditLog synthetic
  vertices in useBezierApply.ts are then IGNORED by compute — it only reads vertices_dict when
  vertex_ops_present). This is the clean path. Do NOT route through BezierEditLayer's store/vertex
  path: it would flip vertex_ops_present true, pull in replay_vertex_ring + the D-25 _carve_n_original
  shrink machinery, AND leave the ghost (which reads op.ring, CanvasViewer.tsx:953) stale while a
  second curve draws from vertices — TWO overlapping previews, violating "ghost follows manipulation".

FACT 4 — CREATE and CARVE are SYMMETRIC pre-Apply.
  SelectionBridge.tsx only populates `${name}#i` vertices for a barony present in effectiveBaronies.
  A freshly-created/carved shape is NOT in effectiveBaronies until the post-Apply refetch (the
  auto-select watcher at CanvasViewer.tsx:456-468 fires post-refetch). So PRE-Apply both create and
  carve exist ONLY as `op:'create'|'carve'` + `op.ring` + the static ghost — neither has vertex keys.
  One manipulation layer reading op.ring handles both. The todo's "behaviour may differ" worry
  dissolves: the only divergence (carve → BezierEditLayer) is POST-Apply, which this plan does NOT touch.

FACT 5 — The ghost overlay (CanvasViewer.tsx:951-975) renders the last editLog op-with-ring as a
  STATIC dashed Line, gated by `pendingSelectName`. Because it reads op.ring, mutating op.ring makes
  it follow natively. While the new interactive layer is active it must SUPERSEDE the static ghost
  (render the live shape itself); the static ghost is the at-rest fallback.

FACT 6 — Re-render + undo granularity (zustand/zundo gotchas, from useEditorStore.ts:481-488):
  (a) editLog is partialized with REFERENTIAL equality. Mutating editLog[i].ring in place will NOT
      re-render consumers — you MUST set a NEW array ref:
      setState({ editLog: editLog.map((op, idx) => idx === i ? { ...op, ring: newRing } : op) }).
  (b) Every new editLog ref = one new zundo history entry. So keep the in-progress drag in
      COMPONENT-LOCAL state (mirrors PenDrawLayer.tsx:8 + BezierEditLayer.tsx:18 "ALL draw state
      component-local"), render the live preview from local state DURING the gesture, and write
      op.ring back ONCE on gesture-end (mouseup) → exactly one undo entry per drag.
</architecture_facts>
