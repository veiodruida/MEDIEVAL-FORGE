# Phase 08.1 Plan 07: G5+G7 Real-Event Usable Bezier Targets — Summary

Screen-space sizing for Bezier anchors/handles/hit-path (BASE/currentScale), MAX_SCALE_MULTIPLIER raised 4→16, and a Playwright spec with REAL page.mouse drag + dblclick proving the fix — both via real Konva hit-testing, no DEV trigger hooks for the claim.

## What Was Built

### Task 1: Raise MAX_SCALE_MULTIPLIER 4 → 16 (`367ee79`)

`frontend/src/hooks/useZoomPan.ts` line 5: single-line cap raise from 4× to 16×. Updated all 6 CanvasViewer test mocks and the useZoomPan constant assertion from 4 to 16.

### Task 2: Screen-space sizing in BezierEditLayer (`a928d0f`)

Added `currentScale: number` prop to `BezierEditLayerProps`. At component top:
```typescript
const safeScale = currentScale > 0 ? currentScale : 1
const anchorSize = ANCHOR_BASE_PX / safeScale    // 10 / scale
const anchorHalf = anchorSize / 2
const handleRadius = (HANDLE_BASE_PX / 2) / safeScale
const hitPathWidth = HITPATH_BASE_PX / safeScale  // 24 / scale (widened for G7)
```

Three "5" desync trap sites all converted to `anchorHalfRef.current`:
1. Anchor Rect offset: `x={a.anchorPx[0] - anchorHalf}`, `y={a.anchorPx[1] - anchorHalf}`
2. `draggedCenterPx`: now takes `anchorHalf` parameter, uses `x + anchorHalf`
3. DEV drag hook `__forgeBezierTriggerDrag`: `targetX = a.anchorPx[0] - anchorHalfRef.current + dx`

Also added `midCurvePoint` read-only field to `__forgeBezierState` — exposes the t=0.5 on-curve point between anchor[0] and anchor[1] in PAGE coords for the G7 dblclick target. Uses `containerRect.left + stage.x() + stagePx.x * stageScale` (correct stage-transform formula).

### Task 3: Thread currentScale into BezierEditLayer (`31585fc`)

```tsx
<BezierEditLayer projection={projection} currentScale={currentScale} />
```
Same `currentScale` state already fed to DecorationsLayer. Live re-renders on every wheel tick.

### Task 4: Playwright UAT — real events + production bug fixes (`adefb6d`)

**New spec** `08.1-bezier-usable-targets.spec.ts` — 3 tests:
- **G5**: Real `page.mouse.down/move/up` drag at 6× zoom commits `op:move`
- **G7**: Real `page.mouse.dblclick` on `midCurvePoint` (mid-segment on-curve point, NOT an anchor) inserts anchor (anchorCount +1, editLog unchanged)
- **BEZ-IDENTITY-01 re-assert**: enter + zero interaction → editLog unchanged

**Two production bugs fixed (Rule 1)** discovered while writing the spec:

1. **`onDblClick` was using wrong coordinate space.** `stage.getPointerPosition()` returns SCREEN-space px (container-relative). `handleInsertAtPx` expects MAP-space px (same as `anchorPx`). At any non-identity scale+pan, these differ by hundreds of pixels → `findNearestSegmentAndVertex` returned null → insert silently failed. **Fix: use `stage.getRelativePointerPosition()`** which inverts the stage transform to return map-space. This bug existed since Plan 06 but was never exposed because `__forgeBezierTriggerInsert` fed map-space directly (bypassing the handler's coordinate conversion). G7 is the first time the real `onDblClick` handler was exercised with real events.

2. **`firstAnchor` page coords omitted stage translation.** The old formula `containerRect.left + getClientRect({relativeTo:stage}).x + width/2` was missing `stage.x()`. `getClientRect({relativeTo:stage})` returns map-space (before stage translation), so `containerRect.left + box.x` was wrong at any panned state. **Fix: `containerRect.left + stage.x() + anchorPx[0] * stage.scaleX()`.**

**Additional DEV hook added**: `__forgePanToFirstAnchor()` — pans the Konva stage so `midCurvePoint` (center of anchor[0]→anchor[1] segment) is at viewport center. Used by the spec to bring the selected barony into view after zoom, since `__forgeSelectBarony` doesn't pan-to-center (unlike condado selection which calls `panToGeoCenter`). DEV-gated, display-only (no store write, no React state change), cleaned up on unmount.

**1. [Rule 1 - Bug] getPointerPosition() → getRelativePointerPosition() in onDblClick**
- **Found during:** Task 4 (G7 real dblclick didn't insert)
- **Issue:** `stage.getPointerPosition()` returns SCREEN-space px; `handleInsertAtPx` expects MAP-space px. At 4× zoom + pan, the coordinates differed by ~500px, causing `findNearestSegmentAndVertex` to always return null.
- **Fix:** Replace with `stage.getRelativePointerPosition()` (inverts stage transform). Added clientX/clientY fallback for robustness.
- **Files modified:** `BezierEditLayer.tsx` (onDblClick handler)
- **Commit:** `adefb6d`

**2. [Rule 1 - Bug] firstAnchor page coords missing stage.x/y translation**
- **Found during:** Task 4 (G5 anchor off-screen even after zoom at anchor coords)
- **Issue:** `getClientRect({relativeTo:stage})` returns map-space px without stage translation. The formula `containerRect.left + box.x` was wrong at any panned/scaled state.
- **Fix:** Compute directly as `containerRect.left + stage.x() + anchorPx[0] * stageScale`.
- **Files modified:** `BezierEditLayer.tsx` (`__forgeBezierState` hook)
- **Commit:** `adefb6d`

**3. [Rule 2 - Missing functionality] __forgePanToFirstAnchor DEV hook**
- **Found during:** Task 4 (barony near edge of map → anchor off-screen after zoom)
- **Issue:** `__forgeSelectBarony` doesn't pan-to-center (only condado selection calls `panToGeoCenter`). After zoom, edge baronies could be off-screen, making real mouse events miss the target.
- **Fix:** Added `__forgePanToFirstAnchor()` DEV hook — pans stage imperatively (no store write) to center the midCurvePoint.
- **Files modified:** `BezierEditLayer.tsx` (DEV hook + cleanup)
- **Commit:** `adefb6d`
