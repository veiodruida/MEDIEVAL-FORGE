## Warnings

### WR-01: G6 reproduction test discovers the active barony but asserts against an arbitrary feature

**File:** `frontend/tests/uat/playwright/08.1-bezier-render-feedback.spec.ts:223-272`
**Issue:** The test computes `baronyId` via `discoverBaronyId` (line 223), but the
`ringBefore` / `ringAfter` snapshots (lines 229-235, 259-265) use a `.find()`
predicate that matches **the first feature with any non-null id** — it never
references `baronyId`. The test then ends with `void baronyId` (line 272) and a
comment claiming the variable is "used implicitly via closure above," which is
false: `baronyId` is dead. The test title and the assertion message
("colored backend barony ring is byte-identical") imply the *selected/active*
barony is being verified, but the code verifies an unrelated arbitrary feature.

This is not a false-green: the assertion still holds because `op:'move'` never
POSTs to the backend, so *every* feature in `baronies.geojson` is byte-identical
before/after. The G6 conclusion is sound. But the scope is misleading (it would
silently pass even if the active barony's ring were the only one that changed),
plus there is a redundant network round-trip (`discoverBaronyId` re-fetches the
same geojson already fetched inside the snapshot evaluates) and a dead variable.

**Fix:** Either tie the snapshot to the discovered barony so the test verifies what
its name claims, or drop the unused discovery and rename to reflect the broader
"backend file unchanged" intent. Targeted version:
```ts
const baronyId = await discoverBaronyId(page, info.project_id)
const ringBefore = await page.evaluate(async ({ pid, bid }) => {
  const res = await fetch(`/api/v3/projects/${pid}/artifacts/baronies.geojson`)
  if (!res.ok) return null
  const fc = await res.json()
  const feat = fc.features?.find((f: { id?: unknown; properties?: { id?: unknown; name?: unknown } }) => {
    const fid = String(f?.id ?? f?.properties?.id ?? f?.properties?.name ?? '')
    return fid === bid
  })
  return feat ? JSON.stringify(feat.geometry?.coordinates) : null
}, { pid: info.project_id, bid: baronyId })
// ...mirror the same predicate for ringAfter; remove the trailing `void baronyId`.
```

## Info

### IN-01: Live edited-contour overlay lacks the all-vertices fallback that the entry-fit has

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:826-838`
**Issue:** The entry-fit `useEffect` filters vertices to the active barony but falls
back to all vertices when no key matches `activeTerritoryId` (line 322:
`ringKeys.length > 0 ? ringKeys : Object.keys(all)`). The `editedRingPts` overlay
`useMemo` filters with the same `keyBarony(k) === activeTerritoryId` predicate but
has no fallback. If a harness or future key scheme ever produced keys that don't
match `activeTerritoryId`, the anchors would still render (fallback path) while the
overlay would be empty, and the G6-fix assertion `editedContourPointCount > 0`
(render-feedback spec line 307) would fail despite a working layer. Latent in
production today because keys do match.

**Fix:** Mirror the entry-fit fallback for consistency:
```ts
const matched = Object.keys(vertices).filter((k) => keyBarony(k) === activeTerritoryId)
const ringKeys = sortRingKeys(matched.length > 0 ? matched : Object.keys(vertices))
```

### IN-02: Overlay stroke width uses an inline magic number instead of a named base constant

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:875`
**Issue:** The edited-contour `<Line>` stroke is `strokeWidth={2.5 / (safeScale)}`
with the `2.5` inlined, whereas every other screen-space size in this component is
derived from a named `*_BASE_PX` constant (lines 230-234: `ANCHOR_BASE_PX`,
`HANDLE_BASE_PX`, `HITPATH_BASE_PX`, `TETHER_BASE_PX`, `CURVE_BASE_PX`). The lone
inline literal is inconsistent and harder to tune. The redundant parentheses around
`safeScale` are also superfluous.

**Fix:** Add `const OVERLAY_BASE_PX = 2.5` beside the other base constants and use
`strokeWidth={OVERLAY_BASE_PX / safeScale}`.
