# Phase 08.1: Code Review Report

**Reviewed:** 2026-05-28T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the Phase 08.1 Bézier-assisted barony contour editing layer: two pure
geometry libs (`bezierFit.ts`, `bezierFlatten.ts`), the `BezierEditLayer` Konva
component, the `CanvasViewer` mount gate, the `EditToolPalette`/`WorkspaceToolbar`
disable-tool wiring, the calibration fixture, and the full unit + Playwright test
suite.

Overall the implementation is careful and well-documented. The non-negotiable
identity contract (BEZ-IDENTITY-01) holds: entry does not write the store, the
commit path uses `op: 'move'` exclusively, only DIRTY segments are flattened,
non-dirty ranges are copied verbatim, snap is anchor-only, and DEV escape hatches
are gated on `import.meta.env.DEV` and cleaned up on unmount. No security issues
and no critical correctness bugs were found.

The findings below are edge-case interaction gaps and minor type/UX issues — none
block the phase contract, but two of the Warnings produce visibly confusing
behavior (a handle that previews movement but never commits).

## Warnings

### WR-01: cp1 of anchor 0 and cp2 of the last anchor preview movement but never commit

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:386-396, 426-430`
**Issue:** The dirty-segment selection rejects out-of-range segments via
`addSeg` (`if (s >= 0 && s < N - 1)`). For a `cp1` drag on anchor `idx === 0`,
`addSeg(idx - 1)` = `addSeg(-1)` is rejected and no other segment is added, so
`dirty` is empty → `changedIds.length === 0` → the handler early-returns with no
commit (line 426-430). Symmetrically, a `cp2` drag on the last anchor
(`idx === N - 1`) calls `addSeg(N - 1)`, which `s < N - 1` rejects. In both cases
`handleDragMove` has already repainted the live preview (line 341), so the user
drags the handle, sees the curve follow, releases, and the change silently
vanishes on dragEnd. The non-editable closing segment (`N-1`) is a documented V1
limitation, but the handles that shape it are still rendered as draggable and give
misleading visual feedback.
**Fix:** Hide or non-draggable-render the two handles that can only shape the
closing segment (anchor 0's `cp1` and the last anchor's `cp2`), so the preview
never promises a commit that won't happen:
```tsx
// when rendering the active anchor's handles, gate the closing-segment handles
const isFirst = a.idx === 0
const isLast = a.idx === anchors.length - 1
// cp1 shapes incoming segment idx-1; cp2 shapes outgoing segment idx
{!isFirst && <Circle /* cp1 */ draggable ... />}
{!isLast  && <Circle /* cp2 */ draggable ... />}
```
Alternatively keep them visible but `draggable={false}` so they read as inert.

### WR-02: post-commit refit does not reconcile activeAnchorIdx — active selection can silently disappear

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:452-470`
**Issue:** After a commit, `handleDragEnd` recomputes `anchors` from the updated
store via `deriveAnchorsFromStore` (line 454) and calls `setAnchors(refit)`, but
never updates `activeAnchorIdx`. If the refit yields a different cubic count than
before the drag (fit-curve can return a different segment count once geometry
changes), `activeAnchorIdx` may now point past the new array. The
`displayAnchors[activeAnchorIdx]` truthiness guard at line 603-604 prevents a
crash, but the active anchor's handles/tethers silently stop rendering, leaving
the user with no selected anchor and no feedback about why.
**Fix:** Clamp or clear the active index after refit:
```ts
setAnchors(refit)
setActiveAnchorIdx((cur) =>
  cur === null ? null : Math.min(cur, refit.length - 1),
)
```
or explicitly `setActiveAnchorIdx(idx < refit.length ? idx : null)` to keep the
just-dragged anchor active when it still exists.

### WR-03: deriveAnchors uses an empty {rangeStart:0,rangeEnd:0} fallback that yields a zero-length flatten range

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:113` (+ `bezierFlatten.ts:45-50`)
**Issue:** When `ranges[j]` is missing, `deriveAnchors` falls back to
`{ rangeStart: 0, rangeEnd: 0 }`. If such an anchor ever becomes a dirty segment
start, `targetCount = rangeEnd - rangeStart + 1 = 1` and `flattenSegment` emits a
single sample at `t = 0` (= p0 only), dropping p3 — a degenerate 1-vertex
re-flatten that collapses the segment. In practice `buildPolyIndexMap` returns one
range per cubic so the fallback should never fire, but the silent zero-length
fallback masks any future indexing regression rather than failing loudly.
**Fix:** Either assert range/cubic length parity in `deriveAnchors`
(`if (ranges.length !== cubics.length) console.warn(...)`) or pick a safer
fallback that spans at least two indices, and guard `flattenSegment` so
`targetCount < 2` still emits both endpoints.

## Info

### IN-01: anchor 0's cp1 handle is coincident with cp2 at entry

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:120, 126`
**Issue:** For `j === 0`, `cp1Px` falls back to `[c1[0], c1[1]]` — the same value
as `cp2Px`. The two handles render exactly on top of each other for the first
anchor, which is visually confusing and (combined with WR-01) makes anchor 0's
`cp1` a meaningless control. Documented as a deliberate fallback, but worth
revisiting alongside the WR-01 fix.
**Fix:** When hiding anchor 0's `cp1` (per WR-01) this becomes moot; otherwise
mirror cp1 across the anchor from cp2 so the two handles are at least distinct.

### IN-02: buildPolyIndexMap forces the last range to the un-deduped index — works only by closing-segment coincidence

**File:** `frontend/src/lib/bezierFit.ts:85-87`
**Issue:** The last range is forced to `inputPxPts.length - 1`. `BezierEditLayer`
(line 282) builds `pxPts` from the *un-deduped* ordered coords (closing duplicate
included), so this assigns the closing-duplicate index to the final cubic. It
happens to be harmless because the final editable segment is `cubics.length - 2`
(the closing segment `N-1` is non-editable), so the forced index lands in the
unused closing range. This correctness depends on a non-obvious invariant.
**Fix:** Add a comment at line 85 stating the forced index is only ever consumed
by the non-editable closing segment, so a future reader does not "fix" it into a
real bug.

### IN-03: 'ESC' cast to EditTool in disabledTools.includes lies about the type

**File:** `frontend/src/components/editor/EditToolPalette.tsx:125`
**Issue:** `disabledTools.includes(key as EditTool)` is called with `key === 'ESC'`,
which is not a member of `EditTool`. It is safe because `Array.prototype.includes`
does runtime string equality and 'ESC' is never in `disabledTools`, but the `as`
cast misrepresents the type for readers and defeats the type checker on this line.
**Fix:** Guard before the cast: `const isDisabled = key !== 'ESC' && disabledTools.includes(key)`,
which narrows `key` to `EditTool` without an assertion.

### IN-04: fallback that fits over ALL vertices when no key matches activeTerritoryId can mask a SelectionBridge keying bug

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:273-276`
**Issue:** When `ringKeys` is empty (no vertex key prefix matches
`activeTerritoryId`), the layer falls back to fitting over `Object.keys(all)` —
every vertex in the store, potentially a multi-barony mishmash. This is documented
as "preserves Plan 02 behavior," but it would silently produce a wrong fit (and a
wrong commit on drag) instead of surfacing a real keying regression in
SelectionBridge.
**Fix:** In DEV, warn when the fallback fires
(`if (import.meta.env.DEV && ringKeys.length === 0) console.warn('no vertices matched activeTerritoryId', activeTerritoryId)`)
so the mismatch is observable rather than absorbed.
