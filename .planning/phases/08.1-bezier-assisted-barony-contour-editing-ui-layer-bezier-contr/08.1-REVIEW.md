## Summary

All four gaps are implemented correctly and test-covered, and the non-negotiable identity
contract (BEZ-IDENTITY-01) holds. No security issues and no critical/warning correctness bugs.

**Identity contract (BEZ-IDENTITY-01) — VERIFIED.** The entry-fit effect
(`BezierEditLayer.tsx:275-308`) computes anchors/ranges/pxPts entirely into component-local
state and refs and never calls `setVerticesAndLog`. The new G3 insert handler
(`handleInsertAtPx`, lines 357-418) is a pure component-local NO-OP: it calls
`setAnchors`/`setActiveAnchorIdx` only and writes nothing to the store. The drag-end early
return (`changedIds.length === 0`, lines 518-522) writes nothing. The sole store write is the
single `setVerticesAndLog(..., { op: 'move' })` chokepoint at line 538. Corroborated by
`useEditorStore.bezierIdentity.test.ts` (mount+unmount, real store) and the
insert-without-drag identity tests in `BezierEditLayer.addpoint.test.tsx` (real store).

**Gap verification:**
- **G1 (closed ring) — closed.** `buildPathData` (lines 101-116) emits exactly N cubic `C`
  commands including the wrap-around closing segment; `buildPolyIndexMap` forces the last
  range's `rangeEnd = M-1` so the closing-duplicate vertex (coincident with anchor 0) has a
  range owner, keeping the ring closed on drag. Covered by `BezierEditLayer.test.tsx` and the
  `buildPolyIndexMap closing-segment coverage` tests.
- **G2 (closing segment editable) — closed.** The dirty-set wrap `(idx - 1 + N) % N`
  (line 479), the `s < N` bound in `addSeg` (line 474), and the `s < N` loop in
  `findNearestSegmentAndVertex` (line 179) make segment N-1 reachable for both anchor and
  handle drags. Covered by the cp1-on-anchor-0 / cp2-on-last-anchor drag tests and the
  closing-segment reachability test in `bezierFit.test.ts`.
- **G3 (insert anchor) — closed.** `splitPolyRange` clamps the split into the strictly-interior
  band and uses the shared-endpoint convention; `findNearestSegmentAndVertex` returns a vertex
  strictly inside the hit segment's range. The new anchor inherits `rightRange`, the split
  anchor takes `leftRange`, and the following anchor's `rangeStart` already equals the original
  `rangeEnd` (shared endpoint), so contiguity is preserved without mutating it. Insert is
  store-safe; first commit happens on a subsequent drag. Covered by `BezierEditLayer.addpoint.test.tsx`.
- **G4 (distinct palette) — closed.** Six exported hex constants (lines 54-59) are pairwise
  distinct, resolving the two prior collisions (CURVE_STROKE vs ANCHOR_INACTIVE_FILL,
  HANDLE_FILL vs TETHER_STROKE).

**Security:** No injection, eval, hardcoded secrets, or unsafe deserialization. The
`window.__forge*` DEV hooks are gated on `import.meta.env.DEV` and removed in the effect
cleanup, so they do not leak into production. Array accesses in the new pure functions

## Info

### IN-01: `dirtyCount` live-preview heuristic does not match the real committed dirty-set

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:428`
**Issue:** `handleDragMove` sets the preview count with
`setDirtyCount(idx === 0 || kind === 'cp2' ? 1 : 2)`, but the authoritative dirty-set in
`handleDragEnd` (lines 471-488) computes membership via `incomingSeg = (idx - 1 + N) % N`:
- an anchor drag marks 2 segments (`incomingSeg` and `idx`) for ALL idx, including idx=0, yet
  the preview reports 1 when `idx === 0`;
- a `cp1` drag on an interior anchor marks 1 segment (`incomingSeg`), yet the preview reports 2;
- only `cp2` (always 1) happens to agree.

This counter is transient display-only state surfaced via
`__forgeBezierState().dirtySegmentCount` and is reset to 0 on dragEnd, so there is no
user-visible or commit-path impact (the UAT spec asserts on `editLogLength`, not this counter).
It is nonetheless a genuine logic inconsistency between preview and commit.

**Fix:** Derive the preview count from the same wrap-aware rule the commit uses. On a closed
ring both the incoming and outgoing segments always exist, so:
```ts
setDirtyCount(kind === 'anchor' ? 2 : 1)
```

### IN-02: "both handles translate" drag test does not discriminate the behavior it names

**File:** `frontend/src/components/canvas/__tests__/BezierEditLayer.drag.test.tsx:187-211`
**Issue:** The test titled "anchor drag translates BOTH control handles by the same delta …"
asserts only that the dragged anchor's own polygon vertex moved
(`after.lat !== before.lat || after.lon !== before.lon`). That assertion would pass whether or
not the control handles are rigidly translated, so it does not guard the rigid-translation
behavior its name claims. The production logic (lines 207-218) is correct — the test simply
doesn't discriminate it.

**Fix:** Assert a property only true when handles translate — e.g. that an interior vertex of an
adjacent dirty segment (shaped by a translated handle) shifts by approximately the same geo
delta as the anchor, or compare against a no-translate baseline.

### IN-03: Header comment miscounts the palette ("5 … colors" then lists six)

**File:** `frontend/src/components/canvas/BezierEditLayer.tsx:29`
**Issue:** The G4 comment states "5 visually distinct colors:" then enumerates six
(green / blue / amber / white / magenta / slate-gray). The six exported hex constants are in
fact all distinct, so G4 is satisfied — only the count word is wrong.

**Fix:** Change "5 visually distinct colors" to "6 visually distinct colors".
