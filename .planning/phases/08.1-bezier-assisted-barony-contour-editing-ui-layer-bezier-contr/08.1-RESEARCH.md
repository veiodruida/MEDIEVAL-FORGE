## Summary

Phase 08.1 replaces the raw "every polygon vertex = a draggable handle" model in `VertexEditLayer.tsx` with a Bézier-assisted control-point model. The key design constraint is that the Zustand store (`useEditorStore.vertices`) NEVER holds Bézier data — it stays polygon-only throughout. Bézier anchors and control handles are DERIVED display state held in component-local state (useRef/useState), computed fresh from the polygon on edit-mode entry and discarded on exit. Only when the user actually drags an anchor does the editing code flatten the affected cubic segment(s) back to polygon vertices and write them into the store.

The parity-safe architecture has one critical design invariant: if no drag ever fires, `setVerticesAndLog` is never called, `editLog` stays empty, and `useEditorStore.vertices` is byte-identical to pre-entry. This makes the empty-log identity contract trivially enforced — no special-case "skip the round-trip" logic is needed because the round-trip path only runs on actual drag commits.

**Primary recommendation:** Use `fit-curve@0.2.0` (MIT, no dependencies, ~300 lines, ships TypeScript types, verified installable) for curve fitting. Hold Bézier display state (anchors + handle positions) in component-local state (useRef/useState) inside a new `BezierEditLayer.tsx`. Keep all Bézier display state entirely outside `useEditorStore` and outside zundo partialize. `activeAnchorIdx` — the index of the last-clicked anchor — is also component-local state, not in the store.

## Architecture Patterns

### Parity-Safe Bézier Architecture (NON-NEGOTIABLE)

The architecture has two parallel data tracks:

```
useEditorStore.vertices   ← polygon-only, zundo-tracked, source of truth
                               (never modified except on actual drag commit)

BezierDisplayState        ← derived, component-local, NEVER in zundo
  anchors: BezierAnchor[]     (computed from polygon on entry; discarded on exit)
  activeAnchorIdx: number | null  (component-local useState — NOT in store)
  dirtySegments: Set<number>  (segments where anchor i or i+1 was dragged)
```

**Entry (barony selected + Bézier mode active):**
1. Read `useEditorStore.vertices` → build ordered polygon coords `[lon, lat][]`
2. Call `fitCurve(coords, errorTolerance)` → produces `[[p0, c1, c2, p3], ...]` cubic segments
3. Build `polyIndexMap[]` — for each cubic segment `j`, record `{ rangeStart, rangeEnd }` covering the original polygon vertex indices it spans (see Split-Index Gap below)
4. Derive anchors from segment endpoints; each anchor carries: `{ anchorIdx, polyVertexRangeStart, polyVertexRangeEnd, anchorPx, cp1Px, cp2Px, originalPolySlice: [lon,lat][] }`
5. Store anchors in component state (useRef or useState) — NOT in useEditorStore
6. `useEditorStore.vertices` is UNCHANGED; `editLog` is UNCHANGED

**During drag (anchor or control-handle moved):**
1. Update anchor/handle position in component state only (local preview, same pattern as existing `previewRef.current`)
2. Repaint via Konva Path `data` update — no store write
3. **Mark BOTH adjacent segments dirty.** Dragging anchor `i` affects segment `i-1` (which ends at anchor `i`) AND segment `i` (which starts at anchor `i`). Both must flatten on commit. `dirtySegments.add(i-1); dirtySegments.add(i)` — with boundary guards for `i=0` and `i=anchors.length-1`. Failing to mark both means the segment on the other side of the anchor retains the pre-drag endpoint, creating a visible discontinuity.

**On drag commit (mouseup / dragend):**
1. For each dirty segment `i` in `dirtySegments`: call `flattenSegment(anchors[i], anchors[i+1], targetVertexCount)` → produces `[lon, lat][]`
2. Build `nextVertices` from original store vertices, replacing only the index ranges covered by dirty segments
3. Call `useEditorStore.getState().setVerticesAndLog(nextVertices, { op: 'move', ... })`
4. Clear `dirtySegments`

**On exit (barony deselected or edit mode exited):**
1. If `dirtySegments` is empty → `useEditorStore.vertices` was never touched → byte-identical to pre-entry ✓
2. Clear anchor state
3. Mid-edit barony switch: `activeTerritoryId` change triggers `BezierEditLayer` teardown. Any uncommitted display-only edits are discarded (only committed drags survived via `setVerticesAndLog`). This is correct behavior — the store has the last committed state.

### Split-Index Gap — CRITICAL PLANNER NOTE

**fit-curve@0.2.0 does NOT expose which original polygon vertex indices each cubic segment covers.** [VERIFIED: github.com/soswow/fit-curve source — `fitCurve` and `fitCubic` return only cubic geometry arrays; internally they slice the input array but the split points are not returned]

The planner must include a Wave 0 task to build `buildPolyIndexMap(inputPoints, cubics)`:
- For each cubic `j`, the segment's endpoint `p3` = `cubics[j][3]` equals `inputPoints[splitIdx]` for some `splitIdx`
- Find each `splitIdx` by locating the nearest input point to each cubic's endpoint (O(N) scan per cubic, or O(N log N) with a sorted map)
- Return `{ rangeStart: number; rangeEnd: number }[]` with one entry per cubic

**Two implementation options:**
- **Option A (recommended):** Post-fit scan — for each cubic `j`, iterate input points from `prevEnd` forward until `inputPoints[k]` is within 1e-4 px of `cubics[j][3]`. This is O(N) total.
- **Option B:** Vendor fit-curve (MIT, ~300 lines) into `src/lib/fitCurveVendored.ts` and patch `fitCubic` to return `{ curves, splitIndices }`. Cleaner but more maintenance surface.

Either option produces the `polyRangeStart/polyRangeEnd` fields needed by `BezierAnchor`. This is a distinct Wave 0 task with its own test.

### Pattern 1: Closed-Ring Curve Fitting

fit-curve operates on open polylines. A barony polygon ring is closed (first point = last point after SelectionBridge drops the duplicate). Two approaches:

**Approach A (recommended — simpler):** Feed the open ring (N points, duplicate dropped by SelectionBridge) directly to `fitCurve`. Accept that the joint between last and first anchor may be slightly discontinuous. For editing purposes this is acceptable — the closing segment is rarely dragged.

**Approach B (smooth closure):** Duplicate first 2 points at end + last 2 points at start before fitting, then trim the resulting curves to the original range. More complex, marginal visual benefit.

**CONTEXT.md says fit quality matters for display, not for the backend.** Approach A is sufficient.

**Closing-segment non-editable (V1):** With Approach A, the logical "segment" from anchor `N-1` back to anchor `0` has no fit-curve cubic — it is not explicitly modeled. In V1, this closing segment is non-editable as Bézier. Dragging anchor `N-1` will mark segment `N-2` dirty (the last cubic); dragging anchor `0` marks segment `0` dirty. The visual discontinuity at the ring closure is a known V1 limitation. Document this in the UI or defer a smooth-closure follow-on. Do NOT attempt to special-case the closing segment in V1 — over-engineering.

```typescript
// Source: [CITED: github.com/soswow/fit-curve README]
// fit-curve signature: fitCurve(points: number[][], error: number): number[][][]
// Each returned curve = [p0, c1, c2, p3] where each point is [x, y] (canvas px)
import fitCurve from 'fit-curve';

function fitPolygonToBezier(
  coords: Array<[number, number]>,  // [[lon, lat], ...]
  errorTolerance: number,           // ~30 yields ~10-20 segments on 200-vertex ring
): BezierCubic[] {
  // Convert geo coords to canvas px BEFORE fitting (fit-curve works in any 2D space)
  // errorTolerance in px units — scale with viewport
  const pts: number[][] = coords.map(([lon, lat]) => {
    const [x, y] = geoToCanvas(lon, lat, projection);
    return [x, y];
  });
  // Drop closing duplicate if present
  const open = pts.length > 1 &&
    pts[0][0] === pts[pts.length-1][0] && pts[0][1] === pts[pts.length-1][1]
    ? pts.slice(0, -1) : pts;

  return fitCurve(open, errorTolerance);
  // Returns: [[[p0x,p0y],[c1x,c1y],[c2x,c2y],[p3x,p3y]], ...]
}
```

### Pattern 2: Flatten Resolution — Density Matching

The goal: when a user edits segment `i`, the re-flattened polygon points for that segment should have approximately the same vertex density as the original polygon's vertices in that range. This prevents the edited segment from being rasterized at a different resolution than unedited segments.

The matching formula: if the original polygon had `M` vertices covering segment `i`'s point range (from `polyVertexRangeStart` to `polyVertexRangeEnd`), subdivide the edited cubic into `M` evenly-spaced parameter steps.

```typescript
// Source: [ASSUMED — inline de Casteljau, standard algorithm]
// Evaluate cubic Bézier at parameter t ∈ [0,1]
function cubicBezierAt(
  p0: [number, number], c1: [number, number],
  c2: [number, number], p3: [number, number],
  t: number
): [number, number] {
  const mt = 1 - t;
  const mt2 = mt * mt;
  const mt3 = mt2 * mt;
  const t2 = t * t;
  const t3 = t2 * t;
  return [
    mt3*p0[0] + 3*mt2*t*c1[0] + 3*mt*t2*c2[0] + t3*p3[0],
    mt3*p0[1] + 3*mt2*t*c1[1] + 3*mt*t2*c2[1] + t3*p3[1],
  ];
}

// Flatten edited segment back to polygon coords matching original density
function flattenSegment(
  cubic: [[number,number],[number,number],[number,number],[number,number]],
  targetCount: number,  // = polyVertexRangeEnd - polyVertexRangeStart (original range size)
  projection: ProjectionState,
): Array<[number, number]> {  // [[lon, lat], ...] — geo coords for store
  const [p0, c1, c2, p3] = cubic;
  const result: Array<[number, number]> = [];
  for (let k = 0; k < targetCount; k++) {
    const t = k / (targetCount - 1);
    const [x, y] = cubicBezierAt(p0, c1, c2, p3, t);
    const [lon, lat] = canvasToGeo(x, y, projection);
    result.push([lon, lat]);
  }
  return result;
}
```

**IMPORTANT:** The fit and flatten happen in CANVAS PIXEL space (not geo-coordinate space) to avoid distortion near poles. The projection is read from `useProjection()`, which is already used throughout `VertexEditLayer.tsx`. Geo coords are only materialized at the store-write step.

### Pattern 3: Konva Rendering — Curve + Anchor + Handle

```typescript
// Source: [CITED: konvajs.org/docs/sandbox/Modify_Curves_with_Anchor_Points.html]

// 1. Curve outline: Konva.Path with SVG cubic path string
// Build "M x0 y0 C c1x c1y c2x c2y x1 y1 C ..." from anchors array
function buildPathData(anchors: BezierAnchor[]): string {
  if (anchors.length === 0) return '';
  const pts = anchors;
  let d = `M ${pts[0].anchorPx[0]} ${pts[0].anchorPx[1]}`;
  for (let i = 0; i < pts.length - 1; i++) {
    const { cp2Px } = pts[i];
    const { cp1Px, anchorPx } = pts[i + 1];
    d += ` C ${cp2Px[0]} ${cp2Px[1]} ${cp1Px[0]} ${cp1Px[1]} ${anchorPx[0]} ${anchorPx[1]}`;
  }
  return d;
}

// 2. Anchor circles: Konva.Circle radius=7, fill='#f0c040', draggable
// 3. Control handle circles: Konva.Circle radius=4, fill='#94a3b8', draggable
//    Only show cp1/cp2 for the ACTIVE anchor (reduces clutter: ~20 anchors × 2 handles = 40 handles)
// 4. Control handle tethers: Konva.Line dashed, listening=false, connecting anchor to its handles
```

**Performance:** `Konva.Path` with updated `data` prop re-parses the SVG string on each render. For real-time drag preview of a single segment, prefer a `Konva.Shape` with `sceneFunc` that calls `ctx.bezierCurveTo` directly — no string parsing. The remaining N-1 segments can be rendered as a static `Konva.Path` and only the dragged segment uses the live shape. ### Pattern 4: zundo partialize — CRITICAL

`useEditorStore` uses:
```typescript
partialize: (s) => ({ vertices: s.vertices, editLog: s.editLog }),
equality: (a, b) => a.vertices === b.vertices && a.editLog === b.editLog,
```

**ANY field added to `useEditorStore` that is NOT in partialize will NOT be tracked by undo — which is correct for Bézier display state.** However, if Bézier display state is added to the store (not recommended), it MUST be outside partialize. The safest approach is to keep all Bézier state entirely outside the store (component local state / useRef) — no risk of accidentally polluting undo history. This explicitly includes `activeAnchorIdx` — keep it in component `useState`, not in the store.

### Anti-Patterns to Avoid

- **Calling `setVerticesAndLog` on edit-mode entry.** This is the silent-rewrite failure mode. `setVerticesAndLog` must be called ONLY when the user drags and commits. Entry must use `temporal.pause() / setState / temporal.resume()` pattern (same as SelectionBridge) — but actually, entry should NOT modify vertices at all. Only the anchor display state is rebuilt.
- **Fitting in geo-coordinate space.** `fitCurve` error tolerance is in the units of the input points. In lat/lon space, the appropriate tolerance is ~0.0001°; near the equator this is ~10m; near poles this distorts differently. Fitting in canvas-pixel space with a pixel error tolerance (~5px) is correct and projection-independent.
- **Adding `op: 'bezier_drag'` to editLog.** CONTEXT.md is explicit: backend never sees Bézier. The `editLog` records polygon-vertex-level ops (`op: 'move'`). A Bézier drag that produces a flatten must write `op: 'move'` (the polygon outcome), not a Bézier-specific op.
- **Rebuilding the entire polygon from Bézier on exit.** Only dirty segments flatten. Unedited segments keep their original polygon vertices byte-verbatim. This is not optional — it is the mechanism that enforces the empty-log identity contract.
- **Marking only one segment dirty per anchor drag.** Dragging anchor `i` affects segments `i-1` AND `i`. Always mark both (with boundary checks). Single-segment marking leaves a discontinuity at the anchor.
- **Showing all 2N control handles at once.** For ~20 anchors, that is 40 small circles on the canvas. Show only the cp1/cp2 of the active (last-clicked) anchor. This is noted as Claude's Discretion but is strongly recommended.
- **Putting `activeAnchorIdx` in `useEditorStore`.** It is display state only. Component-local `useState` is correct.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Curve fitting from polyline | Schneider's algorithm from scratch | `fit-curve@0.2.0` | 200+ lines, numerically sensitive, already the canonical JS port |
| Cubic Bézier evaluation (flatten) | Newton-Raphson arc-length subdivision | 4-line de Casteljau (uniform t) | Arc-length is overkill for density-matching; uniform t is sufficient and produces ~correct density |
| SVG Bézier path rendering in Konva | Custom canvas draw loop | `Konva.Path data="M … C …"` or `Konva.Shape sceneFunc ctx.bezierCurveTo` | Konva handles layer caching, hit-testing, and RAF; don't bypass it |
| ESM import of CJS library in Vite | Rollup plugin shim | Vite auto-transforms CJS to ESM at dev time | fit-curve ships CJS-only; Vite handles it transparently for dev + build |
| Split index recovery | Separate distance search | Post-fit O(N) scan (see Split-Index Gap section) | fit-curve doesn't return split indices; scan is trivial and correct |

**Key insight:** fit-curve is CJS-only (no `type: module`, no `exports` field, `main: lib/fit-curve.js`). Vite 6 automatically transforms CJS dependencies in `node_modules` during dev (via esbuild) and during build (via rollup commonjs plugin). No vite.config change is needed. [VERIFIED: `npm view fit-curve --json` shows no `type` or `exports` fields; Vite's default behavior handles this]

## Critical Implicit Constraints (Not in CONTEXT.md)

These must be addressed in planning — they are derived from the existing Phase 08 codebase:

### 1. Shared-Vertex Coupling (TOPO-04, D-30)
When a Bézier anchor corresponds to a polygon vertex that is shared with a neighbour barony (detected via `buildSharedVertexIndex` / `getCoupledVertices` in `lib/sharedVertex.ts`), the flatten commit must trigger the same coupling logic. The existing `handleDragEnd` in `VertexEditLayer.tsx` already handles this: it calls `getCoupledVertices` before writing to the store. The new `BezierEditLayer` dragend handler must call the same function.

**Concretely:** After building `nextVertices` from the flatten, check each changed vertex ID against `sharedIndexRef` — if coupled, include the partner barony's vertices in `nextVertices` and pass them all to `setVerticesAndLog`.

### 2. Snap Behavior (TOPO-03)
Snap applies to **anchor** drags (they are polygon endpoints). Snap does NOT apply to **control-handle** drags (handles are purely aesthetic; snapping them would be confusing). The existing `snapToNeighbour` function in `lib/snap.ts` is reused for anchor drags; control-handle drags skip snap entirely.

### 3. 1000-Vertex Cap (D-06)
The cap enforces `vertexCount >= 1000` on the polygon in the store. The Bézier model has ~10-20 display anchors, but the underlying polygon still governs the cap. Flatten of an edited segment replaces the original M vertices with M new vertices — no net change to count. The cap is unchanged and need not be reconsidered.

### 4. Add Tool (A) and Delete Tool (D) in Bézier Mode
**A tool:** In Phase 08, the A tool adds raw polygon vertices by clicking an edge. With Bézier mode active, this is non-trivial (requires hit-testing the curve outline to find which segment was clicked, then splitting the polygon vertex range). **Recommendation V1:** Disable A tool when Bézier mode is active. Display a tooltip explaining that adding vertices is available in raw-vertex mode.

**D tool:** Deleting an anchor in Bézier mode means removing the anchor and the polygon vertex range it spans, then re-joining adjacent segments. Non-trivial. **Recommendation V1:** Disable D tool when Bézier mode is active. V-tool drag editing covers the primary use case.

Both disables should be explicit (grey out the A/D buttons in EditToolPalette when Bézier mode is active) rather than silent no-ops.

### 5. SelectionBridge Re-Entry
`SelectionBridge.tsx` rebuilds `useEditorStore.vertices` every time `selectedBaronyId` changes (wrapped in `temporal.pause/resume`). If the user selects a barony, makes Bézier edits (which write back to `vertices`), then re-selects the same barony — SelectionBridge runs again and reloads from `effectiveBaronies.geoRing`. This correctly resets to the committed state (since `setVerticesAndLog` already wrote the flattened edits). `BezierEditLayer` must also reset its anchor display state when `activeTerritoryId` changes — a `useEffect` cleanup handles this.

### 6. fit-curve Error Tolerance Calibration
`fitCurve(points, error)` error is in squared distance units of the input space. In canvas-pixel space:
- `error = 5` → tight fit, many segments (~1 anchor per ~5-8 original vertices), may yield 30-50 anchors for a dense 200-vertex ring
- `error = 50` → loose fit, few segments (~1 anchor per ~15-20 vertices), yields ~10-20 anchors for a 200-vertex ring
- Recommended starting value: `error = 30` (empirical range for ~10-20 anchors on a typical σ=3.0 smoothed Voronoi barony polygon) [ASSUMED — based on algorithm behavior; exact value requires empirical calibration in Wave 0 or a task that tests with a real Iberia barony polygon]

## Common Pitfalls

### Pitfall 1: Calling setVerticesAndLog on Edit-Mode Entry
**What goes wrong:** Any call to `setVerticesAndLog` during entry (even with identical vertices) appends to `editLog` and creates a zundo history entry. The empty-log identity contract is violated. The user enters edit mode, exits without dragging, and the `editLog.length` increased by 1 — `manual_edit.compute()` no longer takes the identity path.
**Why it happens:** Developers assume they must "save" the Bézier-derived geometry back to the store on entry.
**How to avoid:** Entry ONLY reads from the store and builds display state. The store is never written to during entry. Use the `temporal.pause/setState/temporal.resume` pattern ONLY if non-vertex UI state (like `activeTerritoryId`) needs updating — never for `vertices`.
**Warning signs:** `editLog.length` increased after enter+exit cycle without drag; identity test fails.

### Pitfall 2: Float Drift in Flatten Round-Trip
**What goes wrong:** On commit, the flatten produces `[lon, lat]` values computed via `canvasToGeo(cubicBezierAt(...))`. Even for an unedited segment (if mistakenly flattened), these values will differ from the original polygon vertices by floating-point noise (~1e-14°). This breaks byte-equality.
**Why it happens:** Floating-point arithmetic is not lossless; projection round-trips introduce sub-epsilon drift.
**How to avoid:** Only flatten DIRTY segments (those where the user actually dragged). Keep `originalPolySlice` per anchor; for non-dirty segments, use the original vertex values verbatim.
**Warning signs:** `JSON.stringify(before) !== JSON.stringify(after)` after enter+exit with zero drags, even though user didn't drag anything.

### Pitfall 3: fit-curve Returns Fewer/More Curves Than Expected
**What goes wrong:** fit-curve splits segments when the chord deviates beyond `error`. A barony with a very irregular coastline may produce 50+ segments (one anchor per very-curved subsection). The opposite — a very simple straight boundary — may fit to 2-3 segments.
**Why it happens:** The algorithm is adaptive; `error` is not a direct "number of anchors" parameter.
**How to avoid:** Clamp the number of anchors: if `fitCurve` returns > 30 curves, increase error and refit. If < 4, display a warning but allow editing anyway. Expose `error` as an internal constant (not user-facing) initialized to a calibrated value.
**Warning signs:** Canvas covered in tiny anchor circles (too tight) or only 2-3 anchors for a complex barony (too loose).

### Pitfall 4: CJS Import of fit-curve Breaking Tests
**What goes wrong:** Vitest uses ESM by default (same as Vite). fit-curve ships CJS only. In some vitest configurations, CJS packages in `node_modules` are not auto-transformed, causing `require is not defined` errors in test files that import fit-curve.
**Why it happens:** vitest.config.ts (project root) does not set `transformMode` or `deps.inline`. The esbuild transformer that handles CJS may not run.
**How to avoid:** Add `deps: { inline: ['fit-curve'] }` to `vitest.config.ts` test configuration. Alternatively, wrap the fit-curve call in a thin module (`lib/bezierFit.ts`) and mock that module in tests — isolating the CJS boundary. [CITED: vitest.dev/config/#deps-inline — for handling CJS packages in vitest]
**Warning signs:** `Error: require is not defined in ES module scope` or `Cannot find module 'fit-curve'` in vitest.

### Pitfall 5: Phase 08 Verification Lesson — Isolation vs Integration
Phase 08 VERIFICATION.md documents that all unit tests passed but the editor was non-functional in the running app because integration wiring (SelectionBridge, prop threading) was absent. This phase must test INTEGRATION — that selecting a barony shows Bézier anchors in the actual running app, not just that `fitCurve()` returns the right curve objects in isolation.
**Prevention:** Each plan task must have an integration verification step (Playwright or `__forgeEditorState` escape hatch) confirming the feature is reachable in the running app, not just unit-tested in isolation.

## Open Questions

1. **fit-curve error tolerance calibration**
   - What we know: algorithm is adaptive; error ≈ 30 in pixel space is a starting hypothesis
   - What's unclear: exact value for a typical Iberia barony polygon (varies by barony complexity)
   - Recommendation: Wave 0 task — run `fitCurve` on the actual `iberia_868` barony polygon data and count anchors at error=10, 30, 50. Lock the constant empirically.

2. **Konva Path vs Shape for live drag preview**
   - What we know: `Konva.Path` re-parses SVG string on each prop change; `Konva.Shape sceneFunc` calls canvas API directly
   - What's unclear: whether the re-parse overhead is measurable at 60fps for a single-segment update
   - Recommendation: Start with `Konva.Path` (simpler); profile during implementation. If jank observed, switch the dragged segment to `sceneFunc`.

3. **Control-handle symmetry (smooth vs cusp)**
   - What we know: Bézier control handles can be smooth (cp1 mirrored opposite cp2) or cusp (independent)
   - What's unclear: whether a "smooth anchor" constraint (moving one handle mirrors the other) is needed
   - Recommendation: Start with independent handles (cusp); smooth anchors can be a follow-on polish task.

4. **polyIndexMap implementation (split-index gap)**
   - What we know: fit-curve does not return which input-point indices each cubic covers [VERIFIED: source code]
   - What's unclear: whether Option A (O(N) post-fit scan) or Option B (vendor + patch) is preferred
   - Recommendation: Option A — 10-15 lines of code, no maintenance surface. Build as a standalone function `buildPolyIndexMap(inputPts, cubics)` with its own unit test before any flatten code is written.
