# Phase 08.1 Plan 03: Bézier drag-commit (anchor + control-handle) Summary

**`BezierEditLayer` gains the actual editing capability: dragging an anchor (or a control handle of the active anchor) flattens ONLY the adjacent dirty segments back to polygon vertices, copies every non-dirty range byte-verbatim from the store, applies snap (anchors only) + shared-vertex coupling, and commits via a single `setVerticesAndLog(op:'move')` — with the Plan 02 empty-log identity contract still green.**

## What landed

- **Anchor drag** marks BOTH adjacent segments (i-1 and i) dirty with boundary guards (i=0 → only segment 0; i=N-1 → only segment N-2; closing segment N-1 stays non-editable). It rigidly translates both control handles of the dragged anchor by the same px delta so the local curve shape is preserved (no cusp). Anchor px → geo, then `snapToNeighbour` snaps to a neighbour-barony vertex (Alt disables); when snapped, the handle translation is re-derived from the snapped position.
- **Control-handle drag** (active anchor only) moves only the dragged handle, never snaps (RESEARCH constraint 2), and marks only the segment that handle shapes dirty (cp1 → incoming segment i-1; cp2 → outgoing segment i).
- **Dirty-only flatten**: for each dirty segment the cubic is rebuilt in px from the (possibly moved) anchor/handle positions and `flattenSegment(cubic, targetCount, projection)` produces `[lon,lat]` at the original density. `nextVertices` starts as `{ ...store.vertices }` and only the dirty index ranges are overwritten — non-dirty ranges are the verbatim store values (the identity mechanism, RESEARCH Pitfall 2).
- **Shared-vertex coupling**: each changed vertex id is passed to `getCoupledVertices`; coupled partners in neighbour baronies are moved to the same coord before commit (mirrors VertexEditLayer:560-579).
- **Commit**: one `setVerticesAndLog(nextVertices, { op:'move', ts, vertexIds })`. After commit, display state is recomputed from the updated store and the shared/snap indices are rebuilt.
- `__forgeBezierState.dirtySegmentCount` is now live (was hardcoded 0 in Plan 02).

## Identity contract (BEZ-IDENTITY-01) — still GREEN

The Plan 02 byte-identity guard against the REAL store was re-run alongside the new drag tests and stays green: enter+exit with zero drags leaves `useEditorStore.vertices` byte-identical and `editLog.length` unchanged. The dirty-only flatten is what preserves this — no drag means `dirtySegments` is empty means `setVerticesAndLog` is never called.

## Dirty-segment boundary handling note (per <output>)

- Anchor i=0 → only segment 0 dirty (no segment -1). The ring's closing-duplicate vertex (coincident with anchor 0) may still move via shared-vertex coupling — this is correct and intended; the closing SEGMENT (its interior vertices) is never flattened.
- Anchor i=N-1 → only segment N-2 dirty; segment N-1 (the closing segment) has no fit-curve cubic and stays non-editable (V1 limitation, RESEARCH §Pattern 1).
- Control-handle drag respects the same closing-segment guard: dragging cp2 of the last anchor targets segment N-1 (skipped) → no commit fires.
