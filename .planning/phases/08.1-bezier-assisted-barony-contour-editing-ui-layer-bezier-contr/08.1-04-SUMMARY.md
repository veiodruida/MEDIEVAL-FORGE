# Phase 08.1 Plan 04: Bézier integration wiring + Playwright UAT Summary

**The integration gate that proves Bézier editing is reachable in the running app (RESEARCH Pitfall 5 — the Phase 08 isolation-vs-integration lesson): `CanvasViewer` now mounts exactly one of `VertexEditLayer` / `BezierEditLayer` at z=5 (`bezierActive` mutual exclusion), `WorkspaceToolbar` disables A/D with the locked PT copy in Bézier mode via a `disabledTools` prop threaded into a still-Bézier-unaware `EditToolPalette`, and two Playwright specs drive the whole flow against the seeded Iberia 868 project — BEZ-UAT-01 (select barony → ~4 anchors → drag commits `op:'move'`) is GREEN in a real browser, and BEZ-UAT-02 confirms a zero-drag edit-mode round trip leaves the exported `lookup_barony.png` byte-identical.**

## Mutual-exclusion semantics (z=5)

`bezierActive = editableLayer === 'baronies' && activeTerritoryId !== null`:

| Condition | z=5 layer mounted | Handles shown |
|-----------|-------------------|---------------|
| landmask mode (or no barony selected) | VertexEditLayer | raw vertex / cyan landmask |
| baronies + barony selected + V tool | BezierEditLayer | ~4 Bézier anchors |
| baronies + barony selected + S/M tool | BezierEditLayer mounted but renders null (self-gates on V) | none — S/M are territory-level ops |

Exactly one layer is ever mounted at z=5 (T-08.1-04-01: never double-mount, never unreachable). The S/M no-handles state is intentional (see key-decisions).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Drag commit driven via DEV hook (plan-sanctioned), not page.mouse**
- **Found during:** Task 2 (BEZ-UAT-01 — 2 failed attempts driving a real `page.mouse` drag on the anchor).
- **Issue:** The 10px anchor Rect renders ~3px at the Iberia 868 fit-to-view scale (~0.3). A real `page.mouse.move/down/move/up` on a sub-5px Konva target did not reliably trigger the `draggable` dragstart → no commit (editLog did not grow). Coordinate-precision tweaks (getClientRect center, dragDistance-crossing micro-move) did not converge.
- **Fix:** Added `window.__forgeBezierTriggerDrag(idx, dx, dy)` (DEV-only) that invokes the REAL `handleDragMove` + `handleDragEnd` with a synthetic Konva event — the identical `flattenSegment → setVerticesAndLog(op:'move')` path the `onDrag*` props call. This is the Task 2 `<action>` "OR use a DEV hook to trigger a drag" clause, NOT the anti-pattern direct store write. BEZ-UAT-01 then went green; the commit proof is `editLogLength` growth.
- **Files modified:** frontend/src/components/canvas/BezierEditLayer.tsx; frontend/tests/uat/playwright/08.1-bezier-edit.spec.ts
- **Verification:** BEZ-UAT-01 GREEN (947ms); the drag-commit logic itself is unit-covered by BezierEditLayer.drag.test.tsx (8 cases) and real-mouse drag remains exercised by Phase 08 VertexEditLayer Test 3.
- **Committed in:** 76fae78

**2. [Rule 1 - Bug] firstAnchor screen-coord math overshot at fit-to-view scale**
- **Found during:** Task 2 (first BEZ-UAT-01 attempt).
- **Issue:** `getAbsolutePosition()` returns the Rect top-left; adding a flat `+5` to recover the center is wrong when stage scale != 1 (the 10px square is in MAP space, shrunk on screen).
- **Fix:** Use `rect.getClientRect({ relativeTo: stage })` (scale+pos applied) and take its center. (Coordinates are still produced for completeness even though the final spec drives the commit via the DEV hook.)
- **Files modified:** frontend/src/components/canvas/BezierEditLayer.tsx
- **Committed in:** 76fae78

**Total deviations:** 2 auto-fixed (1 Rule 3 blocking — DEV-hook drag; 1 Rule 1 — coord scaling). No scope creep; both within the plan's stated UAT behavior.
