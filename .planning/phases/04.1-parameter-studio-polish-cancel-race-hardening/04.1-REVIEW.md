## Warnings

### WR-01: Cancelled-stage SSE emits wrong `prior_token` field

**File:** `backend/medieval_forge/api/v3/render.py:162-170`
**Issue:**

In the `StageCancelled` handler, the producer iterates over `completed_stages + [exc.stage_name]` and emits `entry.prior_token` for each:

```python
cancelled_and_completed = list(dict.fromkeys(completed_stages + [exc.stage_name]))
for stage in cancelled_and_completed:
    entry = cache_get(project_id, stage)
    prior_tok = (entry.prior_token if (entry and entry.prior_token) else "") or ""
    _emit(queue, "stage_cancel", stage, prior_tok, None, prior_tok)
```

This conflates two different cases (semantically reversed):

- **Completed stages** in this run: `cache_put` ran, so `entry.token` = the new (in-progress run) value and `entry.prior_token` = the prior-run's value. Reverting via `prior_token` is correct here.
- **Cancelled stage**: `cache_put` did NOT run (atomicity invariant per `cache.py:53` docstring). `entry.token` is still the prior-run's value (the canonical revert target). `entry.prior_token` is two-runs-back, or `None` on a first-render cancel.

Frontend impact: `useRenderStream.ts:70` calls `run.revertStage(stage, msg.message ?? '')`, which writes the empty string into `priorTokens.render`. `CanvasViewer.tsx:238` then evaluates `priorTokens.render !== undefined ? priorTokens.render : cacheVersion`, and because `''` is not `undefined`, `effectiveCacheVersion = ''` — the artifact URLs in `useCanvasArtifacts.ts:136` become `?v=` (empty), bypassing the intended browser cache-bust and arguably worse, the URL no longer matches the warm cached artifact entry.

Existing test `test_cancel_does_not_update_cache` verifies the cache is unchanged on cancel but does NOT assert what token is emitted via SSE for that stage; the bug is silent in the current test matrix.

**Fix:**

```python
for stage in cancelled_and_completed:
    entry = cache_get(project_id, stage)
    if stage == exc.stage_name:
        # Cancelled stage: cache_put did NOT run; entry.token is the prior-run value.
        prior_tok = entry.token if entry is not None else ""
    else:
        # Completed-this-run stage: cache_put ran; prior_token is the revert target.
        prior_tok = (entry.prior_token if (entry and entry.prior_token) else "") or ""
    _emit(queue, "stage_cancel", stage, prior_tok, None, prior_tok)
```

Add a test that pre-seeds `cache_put(pid, 'smooth', 'prior-X', ...)`, cancels before smooth completes, and asserts the emitted `stage_cancel` SSE for stage `smooth` carries `token == 'prior-X'`.

### WR-02: `BackgroundLayer.visible` bound to `layerVisibility.condados` contradicts inline contract comment

**File:** `frontend/src/components/canvas/CanvasViewer.tsx:550-557`
**Issue:**

The comment immediately above the `<BackgroundLayer>` element explicitly states:

```jsx
{/* BackgroundLayer always shows the raster — either visual_condado.png
    (render-final) or /stage/{name}.png (intermediate stage view). */}
<BackgroundLayer
  src={stageRasterUrl}
  mapW={projection.mapW}
  mapH={projection.mapH}
  visible={layerVisibility.condados}
/>
```

But `visible={layerVisibility.condados}` ties the BackgroundLayer's display directly to the "Condados" toggle in `LayerTogglePanel`. When the user toggles condados off (e.g., to inspect baronies alone), the underlying raster vanishes — leaving an empty Stage. This is either (a) a stale comment, or (b) a bug. Either way the contradiction is misleading and the user-visible behavior is jarring (raster disappears when only the vector overlay should).

Stage-view rasters (intermediate views like `cleanup`, `smooth`) almost certainly need to be visible even when condados is off, since vector layers are hidden in stage-overlay views anyway (`isStageOverlay` at line 527).

**Fix:**

Choose one of:

(A) If the intent IS to always show the raster, remove the `visible` prop binding (default is `true`):
```jsx
<BackgroundLayer src={stageRasterUrl} mapW={projection.mapW} mapH={projection.mapH} />
```

(B) If the intent is to gate on condados only in render-final view, but always-on for stage views:
```jsx
<BackgroundLayer
  ...
  visible={isStageOverlay || layerVisibility.condados}
/>
```

Update the comment to match the chosen semantic.

### WR-03: `useParameterStudioDispatch` silently swallows ALL errors from `postRenderCancel`

**File:** `frontend/src/hooks/useParameterStudioDispatch.ts:53`
**Issue:**

```ts
await postRenderCancel(projectId).catch(() => {})
```

The comment at line 14 says "404 treated as success" — but `.catch(() => {})` swallows every error: 500s, network failures, parser errors, timeouts. If the backend is down, the cancel call silently no-ops and the subsequent `postRender(...)` still runs, then `useRunStore.startRender` puts the UI into 'rendering' state, but no SSE will ever arrive. The user sees a spinner that never resolves.

This is intentional latency-vs-correctness trade-off (per the latest-wins design) but the silence is too broad. A 500 from `/cancel` is qualitatively different from a 404 (which legitimately means "nothing to cancel").

**Fix:**

Narrow the swallow to 404-only:

```ts
await postRenderCancel(projectId).catch((e: Error) => {
  // 404 is expected when no render is currently active.
  if (e.message !== 'NOT_FOUND') throw e
})
```

(Confirms with `api/render.ts` cancel implementation — adjust message constant accordingly.) Other failures should bubble into the outer `try/catch` so the user sees `useRunStore.finish('error', msg)` instead of a stuck rendering state.

### WR-04: `_render_producer` accepts an unused `sf` parameter

**File:** `backend/medieval_forge/api/v3/render.py:104-109`
**Issue:**

```python
async def _render_producer(
    project_id: str,
    overrides: dict,
    queue: asyncio.Queue,
    sf,
) -> None:
```

`sf` is passed by the caller (line 221: `_render_producer(project_id, overrides, queue, AsyncSessionLocal)`) but never used in the body — `AsyncSessionLocal` is consumed directly via the module-level import (line 154). This is a misleading API: future maintainers will think `sf` is the session factory dependency-injection seam (it is in `generate.py:_generate_producer:113-117`, which makes the asymmetry confusing).

Either remove `sf` and the caller's pass-in, OR use it (mirroring `generate.py`'s `async with sf() as session:` pattern) so the producer is testable without monkeypatching module-level `AsyncSessionLocal`.

**Fix:**

Mirror generate.py — use `sf` instead of `AsyncSessionLocal`:

```python
async def _render_producer(project_id, overrides, queue, sf):
    ...
    async with sf() as session:
        proj = await session.get(Project, project_id)
        ...
```

Or remove the parameter entirely and update the caller:

```python
task = asyncio.create_task(
    _render_producer(project_id, overrides, queue),
)
```

The first option is preferable because `test_render_endpoint.py:56` already patches `AsyncSessionLocal` on `v3_generate_mod` (not on `v3_render_mod`), so render-endpoint tests currently rely on the module-level import bypass.

### IN-01: Vacuous-pass guard in zoom-persistence spec is fragile

**File:** `frontend/tests/e2e/parameter-studio-zoom-persistence.spec.ts:99-114`
**Issue:**

With `SCALE_BY = 1.05` (per `useZoomPan.ts:4`), three wheel ticks produce `1.05^3 ≈ 1.157`. The vacuous-pass guard asserts `scaleAfterZoom > initialScale * 1.1` — a margin of only ~5.7%. Under CI load, one missed wheel tick (browser frame drop, ResizeObserver settle, slow Konva batchDraw) drops to `1.05^2 = 1.1025`, well below the 1.1 threshold, producing a spurious failure.

**Fix:**

Either (a) increase the wheel-tick count from 3 to 5 (`1.05^5 ≈ 1.276`, comfortable margin), or (b) lower the threshold to `1.05` and trust that any zoom-in registered is enough to expose a real regression:

```ts
for (let i = 0; i < 5; i++) {
  await page.mouse.wheel(0, -400)
}
```
