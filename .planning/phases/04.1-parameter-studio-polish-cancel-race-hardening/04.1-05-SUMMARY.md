  patterns:
    - "Dev-only escape hatch on window: useEffect gated on `import.meta.env.DEV` mirrors a component's internal state to `window.__forge*`. Production bundles strip the effect entirely (Vite dead-code elimination on `if (!import.meta.env.DEV) return`). Pattern reusable for any future E2E spec that needs deterministic access to runtime state without coupling to DOM details."
    - "Vacuous-pass guard via empirical threshold: `expect(scaleAfterZoom).toBeGreaterThan(initialScale * 1.1)` catches the case where the simulated user interaction (wheel-zoom) silently no-ops. Without it, the SC-1 spec would pass when wheel-zoom is broken — testing nothing. Pattern applies whenever a spec depends on a prior simulated user action having a measurable effect."
    - "Diagnostic-then-remove logging: when an E2E spec fails with an unclear cause, temporarily add `console.log('[CV-*]', ...)` at key effect entry points, capture via `page.on('console', msg => process.stderr.write(msg.text() + '\\n'))`, identify the firing pattern, then strip ALL logging before committing. The log evidence belongs in the SUMMARY, not the shipped code."
    - "keepPreviousData for stage-mounted-during-refetch UI: any UI that holds imperative state in refs (Konva Stage, scroll position, focus) MUST use `placeholderData: keepPreviousData` on its data queries — otherwise the loading branch unmounts the host component and resets all refs. The bug is invisible in unit tests because component lifecycle is mocked away."

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] viewport-key effect clobbering user zoom on every workspace layout micro-shift**

- **Found during:** Task 1 (SC-1 spec exposed it; first run failed at `after=0.15833333` exactly equal to `minScale`).
- **Diagnostic evidence** (captured via temporary console.log + `page.on('console', ...)`):
  ```
  [CV-BOUNDS-KEY-FIRE] 1778504963449 prev= null next= 3840x2160:-13.2,8.2,35.4,44.6
  [CV-FIT] 1778504963450 scale= 0.225625 viewport= 912 624
  [CV-VIEWPORT-KEY-FIRE] 1778504963622 prev= 912x624 next= 640x672
  [CV-FIT] 1778504963622 scale= 0.15833333333333333 viewport= 640 672
  [CV-VIEWPORT-KEY-FIRE] 1778504991482 prev= 640x672 next= 960x672
  [CV-FIT] 1778504991483 scale= 0.2375 viewport= 960 672
  ... 8+ more oscillations through the 56-second run ...
  ```
- **Issue:** Plan 04.1-03's bounds-key gate works correctly for cacheVersion-driven projection-bounds changes. The independent viewport-key effect (intended to handle window resize) fires on every ResizeObserver-reported viewport change — including the 912x624 ↔ 640x672 ↔ 960x672 oscillation that occurs during normal workspace layout settle (sidebar mount, toolbar render, container flex re-measure, refetch-triggered layout reflow). Each oscillation iteration calls `fitToView()` which calls `setMinScale(scale) + setCurrentScale(scale)` — wiping the user's manual zoom.
- **Why 04.1-03 unit tests passed:** the test mocked `useCanvasArtifacts` directly and fired ResizeObserver entries in `act()` — single deliberate measurements, not real-world oscillation.
- **Fix:** gate fitToView in the viewport-key effect on `Math.abs(currentScale - minScale) < 1e-6` — only re-fit when the user hasn't manually zoomed. Legitimate cases (first mount, true window resize before user zoom) still fit because `currentScale === minScale` at those moments. Deps array extended with `currentScale, minScale`.
- **Files modified:** `frontend/src/components/canvas/CanvasViewer.tsx` (viewport-key effect at lines 334-358).
- **Commit:** `6a0a7c4`.
- **Why in scope:** Plan 04.1-05 Task 4's `<action>` explicitly directs the executor to fix regressions in Plans 04.1-01..04 caught by this plan's gate. This bug exists in 04.1-03's implementation; the gate caught it; the fix lands here.

**2. [Rule 1 - Bug] useCanvasArtifacts queries drop CanvasViewer into the "Loading map…" branch on every refetch**

- **Found during:** Task 1 (diagnosed alongside #1; both contribute to the same observable D-01 leak).
- **Issue:** Every slider drag bumps cacheVersion → TanStack refetches the 5 queries → during refetch their `.data` is undefined → CanvasViewer's `if (!metaQ.data || !projection || ...)` guard (lines 499-512) returns the `Loading map…` div instead of the `<Stage>` → Konva Stage unmounts → `stageRef.current = null` AND `prevBoundsKeyRef.current = null` AND `viewportKeyRef.current = ''` → on remount the bounds-key effect treats the next projectionBoundsKey as a real change (`null !== '<key>'`) → fires fitToView. This is the second leak path the SC-1 gate exposed.
- **Why 04.1-03 unit tests passed:** the test fixtures mock `useCanvasArtifacts` directly and immediately return resolved data — the loading branch never executes.
- **Fix:** add `placeholderData: keepPreviousData` (imported from `@tanstack/react-query`) to all 5 query configs. TanStack now keeps the prior `data` available during refetch — CanvasViewer never enters the loading branch on cacheVersion change, Stage never unmounts.
- **Files modified:** `frontend/src/hooks/useCanvasArtifacts.ts` (import + 5 query configs).
- **Commit:** `6a0a7c4`.
- **Why in scope:** same as #1 — caught by the gate Task 4 mandates. Both fixes are independent and both are necessary; either alone is insufficient to make SC-1 green.
