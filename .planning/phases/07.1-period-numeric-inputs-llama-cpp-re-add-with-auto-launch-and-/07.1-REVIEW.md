## Warnings

### WR-01: `_is_outer_session` leaks two unclosed `AsyncSession` connections per research run

**File:** `backend/medieval_forge/services/research/runner.py:218`

**Issue:** `_is_outer_session(session_factory)` is called from the `finally` block at line 218, every time a research producer finishes. Inside that helper (lines 282-283) it calls `session_factory()` twice to compare object identity. In production `AsyncSessionLocal` is not a `lambda` returning the same object — each call allocates a new `AsyncSession` and checks out a connection from the SQLAlchemy pool. Neither probe session is ever closed or awaited, so two connections are leaked to the pool on every research run completion.

On a single-user local app the pool size is unlikely to be exhausted, but under rapid repeated research submissions (or during test suite runs that call `start_research` many times) the pool can fill and subsequent sessions will block or timeout.

**Fix:** Replace the call-twice-and-compare approach with a sentinel-based flag injected by the test fixture, or type-check the factory rather than probing it at runtime:

```python
# Option A — add a flag attribute to the test lambda
# In the test fixture:
#   factory = lambda: db_session
#   factory._is_outer = True
# In runner.py:
def _is_outer_session(session_factory) -> bool:
    return bool(getattr(session_factory, "_is_outer", False))

# Option B — pass explicit bool from start_research
async def start_research(
    ...
    session_factory: Callable[[], Any],
    _outer_session: bool = False,   # test seam; production callers leave False
) -> str:
    ...
    # pass _outer_session into _research_producer; remove _is_outer_session entirely
```

Either option eliminates the two probe calls and the associated connection leak.

### WR-02: `hs = None` dead assignment leaves `healthy`/`message` undefined when `health_check` raises

**File:** `backend/medieval_forge/api/v3/research.py:232-237`

**Issue:** In the `else` branch of `get_providers` (providers that implement `health_check` but not `health`), the `except` block assigns `hs = None` at line 232, then assigns `healthy = False` and `message = str(exc)`. The `hs = None` assignment is never subsequently read — the code reads `hs.healthy` / `hs.message` only in the `else:` clause of the `try/except` (line 235-237), which does not execute on exception. The dead assignment is harmless today, but if a maintainer later adds logic that reads `hs` after the `except` block (e.g., to read `hs.available_models`), they will get an `AttributeError` from the `None` object without realising the assignment was always a no-op.

Additionally, `hs.available_models` is never read in this branch even though `HealthStatus` carries the field (D-09). Any provider that returns `available_models` via `health_check()` (rather than `health()`) will silently drop the model list in the providers response. This contradicts the D-09 schema extension stated purpose.

**Fix:**
```python
else:
    try:
        hs = await provider.health_check(None)
    except Exception as exc:  # noqa: BLE001
        healthy = False
        message = str(exc)
        available_models = None   # explicit, no dangling `hs`
    else:
        healthy = bool(hs.healthy)
        message = hs.message
        available_models = (
            list(hs.available_models) if hs.available_models is not None else None
        )
```

Remove the `hs = None` line entirely so the variable's scope is clear.

### IN-01: `_STARTED_AT` read outside lock after being written inside it

**File:** `backend/medieval_forge/services/llm/llamacpp_launcher.py:207`

**Issue:** `_STARTED_AT` is assigned inside `_STATE_LOCK` at line 200 and then read outside the lock at line 207 to build `LaunchResult.started_at`. In CPython this is safe in practice (single-assignment of an immutable `str`), but it is technically an unsynchronized read of a shared module-level variable. A future port to a free-threaded Python build (PEP 703) or a non-CPython runtime would make this a real race.

**Fix:** Capture the value inside the lock and return it:
```python
with _STATE_LOCK:
    ...
    _STARTED_AT = datetime.now(timezone.utc).isoformat()
    started_at_snapshot = _STARTED_AT          # capture while holding lock

return LaunchResult(
    ok=True,
    base_url=f"http://127.0.0.1:{port}",
    pid=proc.pid,
    model=model_filename,
    started_at=started_at_snapshot,            # use snapshot, not module global
)
```

### IN-02: `conint(ge=1, le=2100)` uses Pydantic v1 compatibility shim

**File:** `backend/medieval_forge/api/v3/research.py:81-82`

**Issue:** `conint(ge=1, le=2100)` is a Pydantic v1-style constrained type that is re-exported as a compatibility shim in Pydantic v2. The `# type: ignore[valid-type]` comments on both lines confirm mypy already flags this as non-standard. If the compatibility shim is removed in a future Pydantic release the validation will silently become a no-op.

**Fix:** Use the Pydantic v2 idiomatic form:
```python
from typing import Annotated
from pydantic import Field

period_start: Annotated[int, Field(ge=1, le=2100)]  # D-01
period_end: Annotated[int, Field(ge=1, le=2100)]    # D-01
```

This removes both `# type: ignore` suppressions and is forward-compatible.

### IN-03: `ResearchDialogHarness` passes empty `condadoIds` — Playwright specs never exercise the condado list path

**File:** `frontend/src/test-routes/research-dialog.tsx:38`

**Issue:** The harness hard-codes `condadoIds={[]}`. The `research_period_numeric.spec.ts` submit-payload test captures the POST body and verifies `period_start`/`period_end` are integers, but it does not verify that `condado_ids` is the correct list from the project. Since the harness passes `[]`, the spec will pass even if the dialog never threads `condadoIds` from the project into the request body. This is a gap in e2e coverage, not a runtime bug.

**Fix:** Either document this as a known harness limitation in the test file header, or add a `condadoIds` search-param to the harness and update the spec to pass a non-empty list and assert it in the captured body.

### IN-04: `research_period_numeric.spec.ts` uses `page.waitForTimeout(300)` to wait for provider query to settle

**File:** `frontend/tests/uat/playwright/research_period_numeric.spec.ts:113`

**Issue:** `await page.waitForTimeout(300)` is a time-based wait that can produce flaky results on slow CI runners. The comment says "Wait for provider query to settle (so canSubmit becomes true)", which is a network-state condition.

**Fix:** Replace with a Playwright condition wait that observes the actual state:
```typescript
// Wait until the submit button is enabled instead of sleeping
await expect(page.getByRole('button', { name: /iniciar pesquisa/i })).toBeEnabled({
  timeout: 5_000,
})
```
