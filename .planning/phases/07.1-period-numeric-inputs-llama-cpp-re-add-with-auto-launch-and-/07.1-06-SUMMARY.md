## What Was Built

### Task 2 — useLlamacppHealth + useLlamacppLaunch + useLlamacppShutdown

**`frontend/src/api/useLlamacppHealth.ts`** (~56 LOC):
- Filters `GET /api/v3/research/providers` to the `llamacpp` entry — no new backend endpoint
- `LlamacppHealth`: `{healthy: bool, message: string, available_models: string[]}`
- `queryKey: ['llamacpp-health']`; `staleTime: 10s`; no polling (UI-SPEC §Interaction Contract)
- `enabled` flag gates the query (pass `isOpen` from AuthSetupSheet)

**`frontend/src/api/useLlamacppLaunch.ts`** (~109 LOC):
- `useLlamacppLaunch`: `POST /api/v3/llm/llamacpp/launch` with `{model}` body
  - `LaunchResult`: `{ok, base_url, pid, model, started_at}` (all 5 fields)
  - HTTP `detail` bubbled as `Error.message` for inline 409 conflict rendering
- `useLlamacppShutdown`: `DELETE /api/v3/llm/llamacpp/launch`
  - `ShutdownResult`: `{ok, was_running}` per Discretion #7 (idempotent 200)
- Both mutations invalidate THREE queryKeys on success (Pitfall 9 + review-fix #6):
  - `['v3', 'research', 'providers']` — ResearchDialog ProviderSelector refresh
  - `['llamacpp-health']` — AuthSetupSheet model dropdown refresh
  - `['llamacpp-status']` — AuthSetupSheet isRunning badge immediate refresh

### Task 3 — useLlamacppStatus hook

**`frontend/src/api/useLlamacppStatus.ts`** (~48 LOC):

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocker] GET /api/v3/projects/{id} does not exist**
- **Found during:** Task 1 investigation
- **Issue:** Plan specified `GET /api/v3/projects/{id}` but `backend/medieval_forge/api/v3/projects.py` only has POST. The plan's own action block says "Do NOT invent a new endpoint — Phase 05 already serves project detail."
- **Fix:** Used `GET /api/projects/{id}` (v1 legacy route in `backend/medieval_forge/api/projects.py`) which returns `ProjectResponse` with `period_start: int | None` and `period_end: int | None` (schemas.py lines 101-102). Documented with comment in file.
- **Files modified:** `frontend/src/api/useProject.ts`
- **Commit:** `ee4a818`

**2. [Rule 1 - Bug] queryKey ['providers'] would silently break Pitfall 9 mitigation**
- **Found during:** Task 2, cross-referencing with useProviders.ts
- **Issue:** Plan's `useLlamacppLaunch` / `useLlamacppShutdown` onSuccess invalidate `['providers']`. But `frontend/src/api/useProviders.ts` (Phase 07) registers `queryKey: ['v3', 'research', 'providers']`. TanStack v5 invalidateQueries does prefix matching — `['providers']` would NOT match `['v3', 'research', 'providers']`, so the ResearchDialog ProviderSelector would never refresh after launch/shutdown.
- **Fix:** Used the actual queryKey `['v3', 'research', 'providers']` in all three mutation onSuccess callbacks. The acceptance criteria grep for `['providers']` — semantically satisfied (providers query IS invalidated), just not with the literal string the criterion specified.
- **Files modified:** `frontend/src/api/useLlamacppLaunch.ts`
- **Commit:** `6cb15ff`

**3. [Rule 2 - Missing] useLlamacppLaunch/Shutdown already invalidate ['llamacpp-status']**
- **Found during:** Task 3 planning
- **Issue:** Task 3 instructs to update Task 2's mutations to add `['llamacpp-status']` invalidation as a second step. Task 2 was written anticipating Task 3's requirement (per must_haves.truths) so both mutations already include the third invalidation.
- **Fix:** No additional edit needed — both mutations correctly invalidate all three queryKeys. Task 3 only required creating `useLlamacppStatus.ts`.
- **Files modified:** None (already correct in Task 2 commit)
