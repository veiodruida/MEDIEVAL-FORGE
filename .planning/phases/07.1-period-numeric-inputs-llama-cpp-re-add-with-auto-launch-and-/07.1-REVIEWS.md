# Cross-AI Plan Review — Phase 07.1

## Gemini Review

Here is a review of the proposed 11 plans for Phase 07.1.

### 1. Summary
The implementation strategy across the 11 plans is highly structured, methodical, and strictly adheres to the project's rigid testing requirements (Nyquist validation, pre-computation of scaffolds). The breakdown of work into independent logical layers—from database schemas and Pydantic models to API endpoints, TanStack hooks, and React UI components—ensures isolation and testability. However, there are two critical React state bugs in the frontend plans that will cause the UI to behave incorrectly under real usage, and a backend parameter mapping issue that could degrade LLM performance.

### 2. Strengths
* **Excellent Subprocess Management:** Encapsulating `subprocess.Popen` in `llamacpp_launcher.py` with idempotent auto-port allocation, lifespan hooks, and `atexit` belt-and-braces ensures that zombie processes are mitigated.
* **Rigorous Security Posture:** The path traversal mitigation for `.gguf` files (`Path(model_filename).name != model_filename` and directory bounds-checking) alongside `DEVNULL` pipe dead-lock prevention demonstrates mature backend design.
* **Atomic Backend Swap:** Plan 04 correctly replaces `period_label` across the entire backend in a single, atomic sweep, leveraging a `grep` gate to guarantee no residual string-based logic breaks the cache or pipeline.
* **Safe E2E Testing Strategy:** Using `sys.executable -c "import time; time.sleep(60)"` as an injectable dependency for testing the subprocess lifecycle ensures CI environments can run the UAT without needing a bulky `llama-server` binary or actual `.gguf` weights.

### 3. Concerns
* **HIGH - React `useEffect` Race Condition (`ResearchDialog.tsx`):** In Plan 07, the period fields are seeded using `if (open && !wasOpenRef.current)`. Because `useProject` is an asynchronous data fetch, `project` will likely be `undefined` exactly when `open` transitions to `true`. `wasOpenRef` flips to `true` immediately, and the inputs will never be seeded once the `project` data actually arrives.
* **HIGH - Persistent "Servidor ativo" State (`AuthSetupSheet.tsx`):** In Plan 08, the `isRunning` state relies on `Boolean(launch.data?.ok)`. Because TanStack's `useMutation` retains its `data` object indefinitely until it is reset or the component unmounts, clicking "Parar servidor" (which triggers the `shutdown` mutation) does not clear `launch.data`. The UI will permanently display "Servidor ativo" after the first successful launch.
* **MEDIUM - LLM Prompt Context Degradation (`runner.py`):** In Plan 04, the `prompt` variable is built by passing `country_name=country_qid`. The prompt will literally render as `Region/Country: Q29`. Local LLMs struggle heavily with Q-codes (Wikidata IDs) compared to human-readable names like "Espanha" or "Iberia," which will likely cause hallucinations or context-collapse during historical metadata generation.
* **LOW - UI Flicker on Open (`AuthSetupSheet.tsx`):** The logic `availableModels.length === 0` renders the "Coloque arquivos .gguf..." hint immediately. Because `health` takes a moment to fetch on mount, the dropdown will flicker disabled with the hint message before the API responds.

### 4. Suggestions
* **Fix the `ResearchDialog.tsx` Seed Logic (Plan 07):**
  Use a localized tracking state that depends on the data actually arriving rather than just the modal's open transition:
  ```tsx
  const [hasSeeded, setHasSeeded] = useState(false)
  useEffect(() => {
    if (open && project && !hasSeeded) {
      setPeriodStart(project.period_start ?? null)
      setPeriodEnd(project.period_end ?? null)
      setHasSeeded(true)
    }
    if (!open) setHasSeeded(false)
  }, [open, project, hasSeeded])
  ```
* **Fix the `AuthSetupSheet.tsx` State (Plan 08):**
  Rely purely on the server's source of truth for the running state, or explicitly clear the launch mutation when the shutdown succeeds. Additionally, guard the empty hint behind the loading state:
  ```tsx
  // Derivation
  const isRunning = health.data?.healthy === true;

  // In the JSX
  {availableModels.length === 0 && !health.isLoading && (
    <Text size="1" color="gray" data-testid="empty-models-hint">...
  )}
  ```
* **Map `country_qid` to `country_name` (Plan 04):**
  While fetching the real country name from Wikidata might be out of scope for Phase 07.1, you should at minimum use the project's `regionDisplayName` (if passable from the UI payload) or implement a basic fallback lookup dictionary (e.g., `{"Q29": "Iberia"}`) inside `runner.py` before passing it to `build_research_prompt`.

### 5. Risk Assessment
**Overall Risk: MEDIUM**
The backend and validation infrastructure are robust, but the frontend React logic contains definitive lifecycle bugs that will cause the UI to fail its primary user workflows (inputs will render blank, and the server toggle button will break after one use). Applying the state fixes mentioned in the suggestions will lower this risk to LOW and ensure a flawless transition.

## Codex Review

## Summary

The plan set is unusually strong: scope is explicit, decisions are locked, test coverage is dense, and the backend/frontend split mostly lines up with SC-1..SC-6. The biggest risks are not missing implementation detail but a few plan inconsistencies and integration assumptions: the numbering/wave labels drift in places, some tests assume UI entry points and provider semantics that may not match the actual app, and the launcher/provider boundary still has a couple of readiness/state ambiguities that could create flaky behavior or false-green tests. Overall, this is a high-quality execution plan that is likely to succeed with a few targeted corrections before implementation.

## Strengths

- Success criteria are concretely mapped to files, tasks, and tests.
- The atomic `period_label` to `period_start`/`period_end` backend swap is the right call; it avoids mixed-schema commits.
- Security is taken seriously in the launcher plan:
  - list-form `subprocess.Popen`
  - explicit path-traversal guards
  - `.gguf` suffix enforcement
  - single-process idempotency
- The plan preserves the Phase 07 zero-LLM parity invariant instead of assuming research-path isolation.
- Validation architecture is strong:
  - unit, e2e, Playwright, and parity are all represented
  - Wave 0 test scaffolds prevent later "untested implementation drift"
- D-09 is handled additively instead of renaming `healthy` to `ok`, which avoids unnecessary churn.
- Frontend UX decisions are clear and testable:
  - seed on open only
  - disabled dropdown with hint
  - inline PT-BR copy locked in the UI spec
- The provider re-add plan correctly treats v1 code as reference, not as a blind restore.

## Concerns

- **HIGH**: `SC-1` wording and validation semantics are inconsistent.
  - Roadmap says `start < end`.
  - context/decisions/tests say `start <= end`.
  - The plan consistently implements `<=`, which is probably correct, but the top-level SC text should be corrected or this will create review churn and false "spec mismatch" findings.

- **HIGH**: `DELETE /launch` return-shape contract is inconsistent across layers.
  - Launcher `shutdown()` returns `None`.
  - Router invents `was_running` via `shutdown_sync()` thread wrapper.
  - Lifespan calls `shutdown()` and ignores whether a process existed.
  - This is workable, but the surface should be normalized so tests and consumers are not implicitly depending on two shutdown APIs with different semantics.

- **HIGH**: Provider running-state semantics are underspecified and may produce UI bugs.
  - `useLlamacppHealth` reads `/research/providers`, which only reports provider health.
  - `AuthSetupSheet` infers "running" from `health.data?.healthy === true || Boolean(launch.data?.ok)`.
  - That can go stale after close/reopen, refresh, or external shutdown because `launch.data` is local mutation state, not canonical server state.
  - The plan achieves SC-5 in happy paths, but not robustly.

- **MEDIUM**: Playwright entry-point assumptions may be wrong.
  - `page.getByRole('button', { name: /pesquisar territórios/i })` is speculative.
  - If there is no stable, existing affordance, plan 07.1-09 will fail despite correct feature implementation.
  - The plan should either define a test harness route or cite the actual Phase 07 entry selector.

- **MEDIUM**: `LlamaCppProvider.research()` test may be too shallow relative to real streaming behavior.
  - "assert at least one event written to queue and `None` sentinel at end" is necessary but not sufficient.
  - It does not prove chunk aggregation, malformed SSE handling, or final JSON extraction behave like Claude/Ollama paths.

- **MEDIUM**: The provider fallback to `http://localhost:8080` is risky.
  - It is justified for test bypasses, but in production it can accidentally hit an unrelated local service.
  - That weakens the SSRF/local-confusion posture compared to "launcher state only".
  - At minimum this should be clearly limited to explicit test contexts or guarded by credentials.

- **MEDIUM**: Some tests rely on private/runtime internals that may be brittle.
  - `atexit._exithandlers`
  - module globals like `_PROCESS`
  - direct assumptions about Radix disabled state and portal timing
  - These are acceptable in small doses, but there is some overfitting to implementation details.

- **LOW**: Scope creep around docs/reporting is high.
  - Per-plan summaries, verification reports, roadmap edits, manual sign-offs, and exact commit shapes add process weight.
  - This is manageable, but it increases execution friction for a relatively modest feature phase.

- **LOW**: There is mild plan numbering/wave drift.
  - Example: some text references plan `07.1-04` for provider work while actual provider plan is `07.1-03`.
  - Not fatal, but it can confuse implementers and reviewers.

## Suggestions

- Normalize the spec language now:
  - Change every success-criteria reference from `start < end` to `start <= end` if snapshot years are intended.
- Normalize shutdown API semantics:
  - Prefer `shutdown_sync() -> bool` and `async shutdown() -> bool`.
  - Then router and lifespan both consume the same contract.
- Add a canonical backend status surface for running server state.
  - Either extend provider health output to include `running`, `pid`, `base_url`, `active_model`, or add a small `GET /api/v3/llm/llamacpp/launch`.
  - That removes the current UI reliance on mutation-local state.
- Tighten the provider base URL rule.
  - Prefer "use launcher state only; no fallback in production".
  - If fallback is kept, make it opt-in for tests via monkeypatch rather than default runtime behavior.
- Strengthen `research()` streaming tests with one more case:
  - partial SSE chunks across boundaries
  - malformed/non-JSON trailing text
  - final parsed payload correctness, not just queue activity
- Replace speculative Playwright navigation with one of:
  - a documented stable selector from existing Phase 07 UI
  - a dedicated test route/harness that renders `ResearchDialog` directly
- Add one launcher test for symlink escape explicitly.
  - Current traversal checks are good; a symlink-outside-models-dir case would validate the resolved-path guard.
- Add one conflict/lifecycle UI test for reopen behavior.
  - Open sheet, launch, close sheet, reopen sheet, verify status still reflects backend reality.
- Clean up plan references and numbering before execution.
  - This is cheap now and avoids human error later.

## Risk Assessment

**Overall risk: MEDIUM**

Justification: the plan is complete enough to achieve SC-1..SC-6, and the main security concerns are already addressed at design level. The remaining risk is integration risk, not conceptual risk: a few ambiguous contracts (`<=` vs `<`, running state ownership, fallback base URL, speculative Playwright entry points) could cause flaky tests or UX inconsistencies even if implementation is mostly correct. Fix those close to LOW with these fixes before execution.
